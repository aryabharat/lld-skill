# T3 Builder for `Point(x, y)`?

No. Builder is for objects with many optional fields, where a constructor would take a long run of nulls or easily-swapped arguments. `Point` has two required fields, both always present, with an obvious order. A builder adds a second class, makes it possible to call `build()` without setting `y`, and turns `new Point(3, 4)` into four lines. That is the "Builder for 3 fields" over-engineering mistake.

Use an immutable value type:

```java
public record Point(double x, double y) {
    public static final Point ORIGIN = new Point(0, 0);

    public Point translate(double dx, double dy) { return new Point(x + dx, y + dy); }
    public double distanceTo(Point o) { return Math.hypot(x - o.x, y - o.y); }
}
```

A `record` gives you the constructor, accessors, `equals`/`hashCode`/`toString`, and immutability for free (on pre-16 Java, a `final` class with two `final` fields does the same).

If you need validation (for example, no NaN), put it in the compact constructor:
```java
public record Point(double x, double y) {
    public Point {
        if (Double.isNaN(x) || Double.isNaN(y)) throw new IllegalArgumentException("NaN coordinate");
    }
}
```

If readability at the call site is the worry (`new Point(lat, lng)` vs `(lng, lat)`), a named static factory solves it without a builder: `Point.ofXY(3, 4)`, or for geo, a separate `LatLng` type so the compiler catches the swap.

Tests worth having: equal points are `equals` and share a `hashCode` (so they work as map keys); `translate` returns a new point and leaves the original unchanged; `distanceTo` of (0,0) and (3,4) is 5; NaN is rejected if you added the check.

When I would revisit: if `Point` grows several optional attributes (z, label, colour, SRID, precision) and call sites start passing defaults positionally. At that point it is probably not a `Point` any more, and that is when a builder (or a separate type) earns its place.
