# T2 Draw after 50 moves

## The change
This is one more rule in an existing chain, so the smallest correct change is one more `if`, placed **after** the win checks (a win on move 50 is still a win) and next to the existing draw check. No pattern needed: the method is six lines and reads top to bottom. I would not introduce a rule/strategy list for one added condition.

```java
class GameEngine {
  static final int DEFAULT_MOVE_LIMIT = 50;

  private final int moveLimit;

  GameEngine() { this(DEFAULT_MOVE_LIMIT); }
  GameEngine(int moveLimit) {
    if (moveLimit < 1) throw new IllegalArgumentException("moveLimit must be >= 1");
    this.moveLimit = moveLimit;
  }

  GameState getState(Board b) {
    if (rowWin(b)) return GameState.win(b.lastPlayer());
    if (colWin(b)) return GameState.win(b.lastPlayer());
    if (diagWin(b)) return GameState.win(b.lastPlayer());
    if (revDiagWin(b)) return GameState.win(b.lastPlayer());
    if (b.isFull() || b.moveCount() >= moveLimit) return GameState.draw();
    return GameState.inProgress();
  }
}
```

And the board owns the count, since it is the thing that sees every move (Tell, Don't Ask: the engine asks the board a question, it does not count moves itself):

```java
class Board {
  private int moveCount;              // incremented in the one place moves are applied

  void place(int row, int col, Player p) {
    // existing validation + cell write ...
    moveCount++;
  }

  int moveCount() { return moveCount; }
}
```

If `Board` already exposes the number of filled cells and moves are never undone, `moveCount()` can just return that; if there is an undo, decrement in undo so the count stays equal to moves actually on the board.

### Decisions worth stating in the PR
- **"Moves" means total moves by both players** (not 50 per player). If product meant per player, the limit becomes 100; the constant is the only change.
- **Win beats the limit.** A move that wins on exactly move 50 returns `win`, not `draw`. Order of the `if`s encodes this and a test pins it.
- **`>=` not `==`.** If anything ever lets a move through after the limit (a caller that doesn't check state), the game still reports draw rather than silently becoming in-progress again.
- The limit is a constructor parameter with a default of 50 so tests can use a small limit on a small board, and so a 3x3 board (which fills at 9 moves and never reaches 50) is not the only thing we can test with.
- `getState` stays a pure function of the board, so no new state in `GameEngine` beyond the config.

## Tests (written first)
```java
@Test void drawWhenMoveLimitReachedWithoutWin() {
  Board b = boardWithMovesAndNoWin(50);            // e.g. on a 10x10 board
  assertEquals(GameState.draw(), new GameEngine().getState(b));
}

@Test void inProgressOneMoveBeforeLimit() {
  Board b = boardWithMovesAndNoWin(49);
  assertEquals(GameState.inProgress(), new GameEngine().getState(b));
}

@Test void winOnTheLimitMoveIsAWinNotADraw() {
  Board b = boardWhereMove50CompletesARow();
  assertEquals(GameState.win(b.lastPlayer()), new GameEngine().getState(b));
}

@Test void fullBoardBeforeLimitIsStillADraw() {      // existing behaviour unchanged
  Board b = full3x3BoardNoWinner();                 // 9 moves
  assertEquals(GameState.draw(), new GameEngine().getState(b));
}

@Test void customLimitIsRespected() {
  Board b = boardWithMovesAndNoWin(4);
  assertEquals(GameState.draw(), new GameEngine(4).getState(b));
}

@Test void rejectsNonPositiveLimit() {
  assertThrows(IllegalArgumentException.class, () -> new GameEngine(0));
}

@Test void boardCountsEveryPlacedMove() {
  Board b = new Board(10);
  b.place(0, 0, X); b.place(0, 1, O);
  assertEquals(2, b.moveCount());
}
```

Plus: the existing win/draw tests must pass unchanged, which is the check that the edit did not reorder or break the current rules.

## When I would restructure instead
If a third or fourth end-condition arrives (time limit, resignation, repetition), the `if` chain becomes a `List<EndCondition>` evaluated in order. Not now: one more `||` is clearer than an abstraction with two implementations.
