# T5 Review: `NotificationService`

Verdict: **request changes.** The throttle is not thread-safe, and this runs on concurrent request threads, so it will both send duplicates and can corrupt the map. There are also two product-level bugs (channels throttle each other, important messages are dropped silently) and the test can't catch any of it.

## Blocking

**1. `static HashMap` mutated from many request threads (data race).**
`HashMap` is not safe for concurrent `put`. Concurrent resizes can lose entries or, on older JVMs, loop forever in `get`. There is also no happens-before between threads, so a reader may never see another thread's write. Use a `ConcurrentHashMap`, and not as a static (see 5).

**2. Check-then-act race: the throttle does not throttle under concurrency.**
`getOrDefault` (check) -> `send` (act) -> `put` (record) are three separate steps. Two requests for the same user arriving together both pass the check before either records, and both send. Worse, the record happens *after* a network call, so the race window is as long as the email/SMS provider's latency (tens to hundreds of ms), not nanoseconds. The fix is to **atomically reserve the slot before sending**, e.g. `ConcurrentHashMap.compute`, then send.

**3. One timestamp for all channels.**
The map is keyed by `userId` only, so an email blocks an SMS and a push for the next 60 s. I doubt that's intended (a marketing email would suppress an OTP SMS). Key by `(userId, channel)`. If the product really wants "one notification of any kind per minute", say so in a comment and a test, because it's surprising.

**4. Throttled messages are dropped silently.**
`return` with no signal: the caller can't tell "sent" from "suppressed", nothing is logged, and nothing is counted. For OTPs, password resets or order updates, dropping is a correctness bug, not a rate-limit. Return a result (`SENT` / `THROTTLED`) and let callers decide; exempt or separately limit transactional messages; add a metric for throttled count.

## Should fix

**5. `static` state.** Every instance shares it, tests leak into each other (the second test that sends to the same user in the same JVM within 60 s is throttled by the first test), and it can't be replaced. Make it an instance field and inject the limiter. Also note this is **per JVM**: with N web servers behind a load balancer, a user can receive up to N messages a minute. If the limit must be global, the limiter needs shared state (Redis `SET key NX PX 60000` is the standard one-liner). If per-instance is acceptable for now, write that down.

**6. Unbounded memory.** Entries are never removed; the map grows with every user who ever got a message. Evict entries older than the window (periodic cleanup, or `compute` returning `null`, or a cache with expire-after-write such as Caffeine).

**7. Untestable time.** `System.currentTimeMillis()` is called directly (twice per call, with different values), so the "after 60 s it sends again" behaviour can't be tested without sleeping for a minute. Inject a `java.time.Clock` (or `LongSupplier` of nanos); read it once per call. Wall-clock time can also jump backwards (NTP), which makes the window negative; a monotonic source avoids that.

**8. Send failure handling.** If `send` throws, nothing is recorded, which is reasonable (allow a retry), but with the reserve-first fix you must release the reservation on failure, otherwise a provider error silently blocks the user for a minute. Also: the provider call is on the request thread with no visible timeout; a slow SMS gateway holds request threads. Every client call needs a timeout; ideally these sends go through a job queue with retry/backoff.

## Nits
- The three methods are the same algorithm with a different client and address. Third copy is exactly when to extract (DRY): one `send(user, channel, msg)` over a `Channel` -> `(client, address extractor)` map.
- Missing null/empty checks for email/phone/device token; a user without a phone number will hit a provider error.

## Suggested shape

```java
public enum Channel { EMAIL, SMS, PUSH }
public enum SendResult { SENT, THROTTLED }

/** Allows one event per key per window. Thread-safe, reserve-before-act. */
public final class Throttle {
    private final ConcurrentHashMap<String, Long> lastAllowedAt = new ConcurrentHashMap<>();
    private final LongSupplier nowMillis;
    private final long windowMillis;

    public Throttle(LongSupplier nowMillis, Duration window) {
        this.nowMillis = nowMillis; this.windowMillis = window.toMillis();
    }

    /** Atomically: if outside the window, record now and return the reservation time; else empty. */
    public OptionalLong tryAcquire(String key) {
        long now = nowMillis.getAsLong();
        boolean[] acquired = {false};
        lastAllowedAt.compute(key, (k, last) -> {
            if (last == null || now - last >= windowMillis) { acquired[0] = true; return now; }
            return last;
        });
        return acquired[0] ? OptionalLong.of(now) : OptionalLong.empty();
    }

    /** Undo a reservation if the send failed, but only if nobody else has reserved since. */
    public void release(String key, long reservedAt) { lastAllowedAt.remove(key, reservedAt); }

    /** Call periodically to keep memory bounded. */
    public void evictExpired() {
        long now = nowMillis.getAsLong();
        lastAllowedAt.entrySet().removeIf(e -> now - e.getValue() >= windowMillis);
    }
}
```
(Releasing restores "never sent" rather than the previous timestamp; fine for a 60 s window, and it only removes our own reservation thanks to `remove(key, value)`.)

```java
public final class NotificationService {
    private final Map<Channel, MessageSender> senders;   // EMAIL -> emailClient adapter, etc.
    private final Throttle throttle;

    public NotificationService(Map<Channel, MessageSender> senders, Throttle throttle) {
        this.senders = Map.copyOf(senders); this.throttle = throttle;
    }

    public SendResult send(User u, Channel channel, String msg) {
        String key = u.getId() + ":" + channel;
        OptionalLong reservedAt = throttle.tryAcquire(key);
        if (reservedAt.isEmpty()) {
            metrics.increment("notification.throttled", channel);
            return SendResult.THROTTLED;
        }
        try {
            senders.get(channel).send(u, msg);           // sender resolves address, has a timeout
            return SendResult.SENT;
        } catch (RuntimeException e) {
            throttle.release(key, reservedAt.getAsLong()); // don't block the user because the provider failed
            throw e;
        }
    }
}

public interface MessageSender { void send(User u, String msg); }
```
