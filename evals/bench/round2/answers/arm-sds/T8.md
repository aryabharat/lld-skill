# T8 Refactor `DiscountCalculator`

## What is actually forcing the change
Three requirements, each of which the current `if` chain can't absorb:
1. **A new rule every week**: today each one is an edit to the same method, so every change risks every other rule (classic OCP trigger: a growing `if` chain).
2. **Some rules must not stack**: the method can only add; it has no notion of "pick one of these".
3. **Finance needs to know which rules applied, and for how much**: the method returns a single `double`, so that information is thrown away. The 30% cap also hides which rule got cut.

So: each rule becomes a small object (Strategy), a calculator applies them with an explicit stacking policy, and the result is an itemised breakdown, not a number. That is one pattern, used because it is needed. No factory, no rule engine, no DSL yet.

## Assumptions
- Money in `BigDecimal` (or `long` paise), not `double`. Rounding HALF_UP to 2 dp, applied per line.
- "Must not stack" is modelled as **exclusive groups**: within a group only the single largest discount applies; across groups discounts add up. This covers "only one coupon", "only one first-order-style promotion", etc. If marketing later needs pairwise rules ("A never with B but either with C"), groups still express most of those; I'd wait for a real case before building more.
- The 30% cap stays a global policy, applied last.
- Today's five rules keep their exact current amounts (verified by characterization tests before touching anything). Note: the two coupon rules can never both fire today (one `coupon` field), so putting them in a `COUPON` group changes nothing now and makes the intent explicit.

## Correctness tests, written first

### Characterization (pin current behaviour before refactoring)
- Premium user, total 2000, no coupon, not first order -> 10% (200) + 50 = 250.
- Total 1000 exactly -> no 50 (strictly greater than).
- WELCOME coupon, total 400, first order -> 20 + 25 = 45.
- FESTIVE in October -> 100; FESTIVE in November -> 0.
- Cap: premium, WELCOME, first order, total 200 -> raw 20+10+25 = 55, cap 60 -> 55; with FESTIVE in October on total 300, premium, first order -> 30+100+25 = 155, cap 90 -> 90.
- Null coupon does not throw.

### New behaviour
- Each applied rule appears in the breakdown with its id and amount; rules that didn't apply don't appear.
- Two rules in the same exclusive group both match -> only the larger appears; tie -> deterministic (lower priority number / rule id).
- Rules in different groups stack.
- Cap: when the sum exceeds 30%, the total equals the cap, and the breakdown shows a `CAP` adjustment line equal to (sum - cap), so `sum(lines) == total` always.
- Invariant: 0 <= total discount <= 30% of order total, and the breakdown sums to the total.
- Adding a rule = one new class + one registration line; the calculator class is not edited (a test registers a new fake rule and sees it applied).

## Design

```java
public record Discount(String ruleId, BigDecimal amount) {}

public interface DiscountRule {
    String id();                          // stable id finance can report on, e.g. "PREMIUM_10"
    String group();                       // exclusive group; rules in the same group don't stack
    Optional<BigDecimal> evaluate(Order o);  // empty = rule doesn't apply
}

public record DiscountResult(BigDecimal total, List<Discount> applied) {}
```

Today's rules. Each is a few lines, testable alone, and the only file touched when it changes:

```java
final class PremiumUserRule implements DiscountRule {
    public String id() { return "PREMIUM_10"; }
    public String group() { return "LOYALTY"; }
    public Optional<BigDecimal> evaluate(Order o) {
        return o.user().isPremium() ? Optional.of(pct(o.total(), 10)) : Optional.empty();
    }
}

final class LargeOrderRule implements DiscountRule {
    public String id() { return "LARGE_ORDER_50"; }
    public String group() { return "ORDER_SIZE"; }
    public Optional<BigDecimal> evaluate(Order o) {
        return o.total().compareTo(new BigDecimal("1000")) > 0 ? Optional.of(new BigDecimal("50")) : Optional.empty();
    }
}

final class CouponPercentRule implements DiscountRule {      // WELCOME
    private final String code; private final int percent;
    CouponPercentRule(String code, int percent) { this.code = code; this.percent = percent; }
    public String id() { return "COUPON_" + code; }
    public String group() { return "COUPON"; }
    public Optional<BigDecimal> evaluate(Order o) {
        return code.equals(o.coupon()) ? Optional.of(pct(o.total(), percent)) : Optional.empty();
    }
}

final class SeasonalCouponRule implements DiscountRule {     // FESTIVE in October
    private final String code; private final Month month; private final BigDecimal amount;
    SeasonalCouponRule(String code, Month month, BigDecimal amount) { this.code = code; this.month = month; this.amount = amount; }
    public String id() { return "COUPON_" + code; }
    public String group() { return "COUPON"; }
    public Optional<BigDecimal> evaluate(Order o) {
        return code.equals(o.coupon()) && o.date().getMonth() == month ? Optional.of(amount) : Optional.empty();
    }
}

final class FirstOrderRule implements DiscountRule {
    public String id() { return "FIRST_ORDER_25"; }
    public String group() { return "FIRST_ORDER"; }
    public Optional<BigDecimal> evaluate(Order o) {
        return o.user().orders() == 0 ? Optional.of(new BigDecimal("25")) : Optional.empty();
    }
}
```
`code.equals(o.coupon())` is null-safe, which removes the repeated `!= null` checks.

The calculator: evaluate everything, keep the best per group, sum, cap, and record every step.

```java
public final class DiscountCalculator {
    private final List<DiscountRule> rules;            // registration order = tie-break order
    private final BigDecimal capPercent;

    public DiscountCalculator(List<DiscountRule> rules, BigDecimal capPercent) {
        this.rules = List.copyOf(rules); this.capPercent = capPercent;
    }

    public DiscountResult calculate(Order o) {
        Map<String, Discount> bestPerGroup = new LinkedHashMap<>();
        for (DiscountRule r : rules) {
            r.evaluate(o).map(a -> a.setScale(2, RoundingMode.HALF_UP)).ifPresent(amount ->
                bestPerGroup.merge(r.group(), new Discount(r.id(), amount),
                    (cur, cand) -> cand.amount().compareTo(cur.amount()) > 0 ? cand : cur));
        }
        List<Discount> applied = new ArrayList<>(bestPerGroup.values());
        BigDecimal sum = applied.stream().map(Discount::amount).reduce(BigDecimal.ZERO, BigDecimal::add);

        BigDecimal cap = o.total().multiply(capPercent).divide(BigDecimal.valueOf(100), 2, RoundingMode.HALF_UP);
        if (sum.compareTo(cap) > 0) {
            applied.add(new Discount("CAP_30", cap.subtract(sum)));   // negative line, so lines sum to total
            sum = cap;
        }
        return new DiscountResult(sum, List.copyOf(applied));
    }
}
```

Wiring, in one place:
```java
var calculator = new DiscountCalculator(List.of(
    new PremiumUserRule(),
    new LargeOrderRule(),
    new CouponPercentRule("WELCOME", 5),
    new SeasonalCouponRule("FESTIVE", Month.OCTOBER, new BigDecimal("100")),
    new FirstOrderRule()),
  new BigDecimal("30"));
```

Finance: persist `DiscountResult.applied` with the order (an `order_discounts(order_id, rule_id, amount)` table, written in the same transaction as the order). Rule ids are stable strings, so reports survive code changes; never reuse an id for a different rule.

## Migration plan (so behaviour doesn't change by accident)
1. Add the characterization tests against the **old** class; they must pass.
2. Introduce the rules + new calculator; keep the old `double discount(Order)` as a thin adapter `calculate(o).total().doubleValue()` so callers don't change in the same PR.
3. Run the same characterization tests against the new calculator; they must pass unchanged.
4. Move callers to `DiscountResult`, start persisting `applied`, delete the adapter.

## Tests (sample)
```java
@Test void sameGroupKeepsOnlyTheLargest() {
    var calc = new DiscountCalculator(List.of(fixed("A", "PROMO", 30), fixed("B", "PROMO", 50)), new BigDecimal("30"));
    var r = calc.calculate(order(1000));
    assertEquals(List.of(new Discount("B", new BigDecimal("50.00"))), r.applied());
}

@Test void differentGroupsStack() { /* A in G1 (30) + B in G2 (50) -> 80, both listed */ }

@Test void capAddsAnAdjustmentLineAndLinesSumToTotal() {
    var r = calculator.calculate(premiumFirstOrderFestiveOctober(300));
    assertEquals(new BigDecimal("90.00"), r.total());
    assertEquals(r.total(), r.applied().stream().map(Discount::amount).reduce(BigDecimal.ZERO, BigDecimal::add));
    assertTrue(r.applied().stream().anyMatch(d -> d.ruleId().equals("CAP_30")));
}

@Test void newRuleNeedsNoCalculatorChange() {
    var calc = new DiscountCalculator(List.of(new FirstOrderRule(), fixed("NEW", "NEW_GROUP", 10)), new BigDecimal("30"));
    assertEquals(new BigDecimal("35.00"), calc.calculate(firstOrder(500)).total());
}

@Test void largeOrderBoundaryIsStrict() {
    assertTrue(new LargeOrderRule().evaluate(order(1000)).isEmpty());
    assertTrue(new LargeOrderRule().evaluate(order(1000.01)).isPresent());
}
```

## Deliberately left for later
- Rules as data (DB/config rows with type + params) so marketing can add a coupon without a deploy. Worth it once most weekly rules turn out to be "coupon X gives Y% / Z flat in date range", which `CouponPercentRule` and `SeasonalCouponRule` already parameterise. Don't build the DSL before seeing a few months of real rules.
- Per-rule caps, ordering-dependent rules (percent applied after flat), and "best combination" search: only when a real rule needs it.
