# T7 Schema: organisations, members, teams, repositories, access grants

## Assumptions
- Postgres, single instance. Even at millions of users/repos this is a comfortable fit; no sharding or separate permission store in v1.
- Repositories are owned by an organisation (user-owned repos are out of scope; adding them later means an `owner_user_id` alternative with a check that exactly one owner is set).
- Membership roles: `member`, `admin`. Org admins have admin access to every repo in the org.
- Repo permission levels are ordered: `read < triage < write < maintain < admin`. Effective permission = the **highest** of: org-admin, org base permission, direct user grant, grants via any team the user is on.
- A team belongs to exactly one organisation and can only be granted repos of that same organisation (enforced in the schema, not just in code).
- A direct user grant may go to a non-member ("outside collaborator"), as GitHub allows. A team member must be an org member.
- No nested teams in v1 (adds a recursive query; listed under later).

## Correctness rules the schema must enforce (written first)
1. A user is in an org at most once, with exactly one role.
2. Repo names are unique per org, case-insensitively.
3. A team grant can only point at a repo in the team's own org.
4. A user can only be on a team if they are a member of that team's org; removing them from the org removes them from its teams.
5. One grant row per (repo, user) and per (repo, team); changing permission is an update, not a second row.
6. Deleting an org deletes its teams, repos and grants; deleting a user deletes their memberships and grants.
7. Every org always has at least one admin. (Not expressible as a simple constraint; enforced in the service, see below.)

## Tables

```sql
CREATE TYPE org_role  AS ENUM ('member', 'admin');
CREATE TYPE repo_perm AS ENUM ('read', 'triage', 'write', 'maintain', 'admin');  -- enum order = rank

CREATE TABLE users (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  login       text NOT NULL,
  email       text NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX users_login_uq ON users (lower(login));
CREATE UNIQUE INDEX users_email_uq ON users (lower(email));

CREATE TABLE organizations (
  id                    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  login                 text NOT NULL,
  base_repo_permission  repo_perm,                      -- NULL = members get nothing by default
  created_at            timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX organizations_login_uq ON organizations (lower(login));

CREATE TABLE org_memberships (
  org_id      bigint NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
  user_id     bigint NOT NULL REFERENCES users(id)         ON DELETE CASCADE,
  role        org_role NOT NULL DEFAULT 'member',
  created_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (org_id, user_id)                          -- rule 1; also serves "members of org X"
);
CREATE INDEX org_memberships_user_idx  ON org_memberships (user_id);            -- "orgs of user Y"
CREATE INDEX org_memberships_admins_idx ON org_memberships (org_id) WHERE role = 'admin';

CREATE TABLE teams (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  org_id      bigint NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
  name        text NOT NULL,
  UNIQUE (org_id, id)                                    -- target for composite FKs (rules 3, 4)
);
CREATE UNIQUE INDEX teams_org_name_uq ON teams (org_id, lower(name));

CREATE TABLE team_memberships (
  org_id      bigint NOT NULL,
  team_id     bigint NOT NULL,
  user_id     bigint NOT NULL,
  PRIMARY KEY (team_id, user_id),
  FOREIGN KEY (org_id, team_id) REFERENCES teams (org_id, id)                       ON DELETE CASCADE,
  FOREIGN KEY (org_id, user_id) REFERENCES org_memberships (org_id, user_id)        ON DELETE CASCADE -- rule 4
);
CREATE INDEX team_memberships_user_idx ON team_memberships (user_id);   -- "teams of user Y", used by access check
CREATE INDEX team_memberships_org_user_idx ON team_memberships (org_id, user_id); -- supports the cascade from org_memberships

CREATE TABLE repositories (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  org_id      bigint NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
  name        text NOT NULL,
  visibility  text NOT NULL CHECK (visibility IN ('public', 'private', 'internal')),
  created_at  timestamptz NOT NULL DEFAULT now(),
  UNIQUE (org_id, id)                                    -- target for composite FK (rule 3)
);
CREATE UNIQUE INDEX repositories_org_name_uq ON repositories (org_id, lower(name));  -- rule 2 + "repos of org X" + lookup by org/name

CREATE TABLE repo_user_grants (
  repo_id     bigint NOT NULL REFERENCES repositories(id) ON DELETE CASCADE,
  user_id     bigint NOT NULL REFERENCES users(id)        ON DELETE CASCADE,
  permission  repo_perm NOT NULL,
  granted_by  bigint REFERENCES users(id) ON DELETE SET NULL,
  granted_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (repo_id, user_id)                         -- rule 5; "collaborators of repo R"
);
CREATE INDEX repo_user_grants_user_idx ON repo_user_grants (user_id);  -- "repos user Y can access directly"

CREATE TABLE repo_team_grants (
  org_id      bigint NOT NULL,
  repo_id     bigint NOT NULL,
  team_id     bigint NOT NULL,
  permission  repo_perm NOT NULL,
  granted_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (repo_id, team_id),                        -- rule 5; "teams with access to repo R"
  FOREIGN KEY (org_id, repo_id) REFERENCES repositories (org_id, id) ON DELETE CASCADE,
  FOREIGN KEY (org_id, team_id) REFERENCES teams (org_id, id)        ON DELETE CASCADE  -- same org_id => rule 3
);
CREATE INDEX repo_team_grants_team_idx ON repo_team_grants (team_id);  -- "repos team T can access"; team-delete cascade
```

### Why these keys
- **Composite primary keys on join tables** (`(org_id, user_id)`, `(repo_id, user_id)`, ...) are the uniqueness rule and the index for the most common direction of lookup at once; no surrogate id needed.
- **The `org_id` copied into `team_memberships` and `repo_team_grants`** is deliberate denormalisation: it lets a plain foreign key prove "team and repo are in the same org" and "team member is an org member". Without it, those rules live only in application code and drift.
- **`ON DELETE CASCADE` from `org_memberships` to `team_memberships`** means removing someone from an org also removes their team access in the same transaction, so there is no window where a former member still reaches private repos through a team.
- **Postgres does not index foreign-key columns automatically.** Every FK whose referenced row can be deleted gets an index on the referencing side (`team_memberships(org_id, user_id)`, `repo_team_grants(team_id)`, ...), otherwise a delete does a sequential scan of the child table under lock.

### Why these indexes (by query)
| Query | Served by |
|---|---|
| Can user U access repo R, at what level? (hot path, every request) | `repositories` PK, `org_memberships` PK `(org_id, user_id)`, `repo_user_grants` PK `(repo_id, user_id)`, `repo_team_grants` PK `(repo_id, team_id)` + `team_memberships` PK `(team_id, user_id)` |
| Repo by URL `org/name` | `repositories_org_name_uq` (with `organizations_login_uq`) |
| Orgs of a user (dashboard) | `org_memberships_user_idx` |
| All repos a user can see | `repo_user_grants_user_idx`, `team_memberships_user_idx` -> `repo_team_grants` PK, `org_memberships_user_idx` for base/admin |
| Members / admins of an org | `org_memberships` PK; partial `org_memberships_admins_idx` for the last-admin check |
| Teams of a repo / repos of a team | `repo_team_grants` PK / `repo_team_grants_team_idx` |

I would not add more indexes until a slow query shows up in `pg_stat_statements`; each index costs on every write.

## The access check
```sql
-- effective permission of :user on :repo, NULL = no access (public repos get 'read' in code)
SELECT max(p) AS permission FROM (
  SELECT 'admin'::repo_perm AS p
    FROM repositories r JOIN org_memberships m ON m.org_id = r.org_id
   WHERE r.id = :repo AND m.user_id = :user AND m.role = 'admin'
  UNION ALL
  SELECT o.base_repo_permission
    FROM repositories r JOIN organizations o ON o.id = r.org_id
    JOIN org_memberships m ON m.org_id = r.org_id AND m.user_id = :user
   WHERE r.id = :repo
  UNION ALL
  SELECT permission FROM repo_user_grants WHERE repo_id = :repo AND user_id = :user
  UNION ALL
  SELECT g.permission
    FROM repo_team_grants g JOIN team_memberships tm ON tm.team_id = g.team_id
   WHERE g.repo_id = :repo AND tm.user_id = :user
) s;
```
Every branch is a primary-key or unique-index lookup, so this is a few index probes, well under a millisecond. `max()` works because the enum is declared in rank order. Wrap it in one method (`AccessService.permission(userId, repoId)`) with tests; don't scatter permission SQL through the codebase. Revocation must take effect immediately, so do not cache this result across requests unless the cache is invalidated on every membership/grant change.

## Rule 7: last admin
In the service, inside one transaction: `SELECT ... FROM org_memberships WHERE org_id = ? AND role = 'admin' FOR UPDATE`; refuse to demote/remove if it would leave zero. The `FOR UPDATE` stops two admins demoting each other concurrently.

## Tests I'd write against a real Postgres (Testcontainers)
- Duplicate membership insert fails; repo name `Foo` vs `foo` in the same org fails, in different orgs succeeds.
- Granting team of org A on a repo of org B fails with an FK violation.
- Adding a non-member to a team fails; removing a user from the org removes their team memberships.
- Access check: no relation -> NULL; direct `read` + team `write` -> `write`; org admin -> `admin`; base permission applies to members only, not outside collaborators.
- Deleting a team removes its grants; deleting an org removes everything under it.
- Concurrent demotion of the last two admins: exactly one succeeds.
