# Add "draw after 50 moves without a win"

## Assumptions
- "50 moves" means 50 moves made in total in this game (both players combined). If it means 50 moves *since the last capture/progress* (chess-style 50-move rule), the counter would reset on that event; the shape of the change is the same.
- A win on the 50th move is still a win: win checks come first.
- `Board` already tracks moves (it knows `lastPlayer()`), so it can expose a move count.

## Change

Keep the order: wins first, then draw conditions. Make the limit a constructor parameter instead of a magic number so tests and other variants can set it.

```java
class GameEngine {
  static final int DEFAULT_MOVE_LIMIT = 50;
  private final int moveLimit;

  GameEngine() { this(DEFAULT_MOVE_LIMIT); }
  GameEngine(int moveLimit) {
    if (moveLimit <= 0) throw new IllegalArgumentException("moveLimit must be positive");
    this.moveLimit = moveLimit;
  }

  GameState getState(Board b) {
    if (rowWin(b) || colWin(b) || diagWin(b) || revDiagWin(b)) {
      return GameState.win(b.lastPlayer());
    }
    if (b.isFull() || b.moveCount() >= moveLimit) return GameState.draw();
    return GameState.inProgress();
  }
}
```

And in `Board`, if it does not exist yet:

```java
private int moveCount;
void place(Position p, Player player) {
  // existing validation + placement
  moveCount++;
}
int moveCount() { return moveCount; }
```

The move count belongs on `Board` (or the game's move history), not in `GameEngine`: `getState` is a pure function of the board today, and keeping it that way means it stays safe to call any number of times. A counter inside the engine incremented in `getState` would be wrong because callers may call `getState` more than once per move.

Also make sure the move loop refuses moves once the state is not `IN_PROGRESS`, otherwise a 51st move could be played after the draw.

I deliberately did not introduce a `List<EndCondition>` strategy chain for this. One extra condition does not justify it. If more end rules arrive (resign, timeout, threefold repetition), that is the point to extract `WinCondition`/`DrawCondition` interfaces.

## Tests
- 49 moves, no win -> `IN_PROGRESS`.
- 50 moves, no win -> `DRAW`.
- Win completed on move 50 -> `WIN` for that player (win beats the move limit).
- Board full before 50 moves -> `DRAW` (existing behavior unchanged).
- `new GameEngine(3)` draws after 3 moves (limit is configurable); `new GameEngine(0)` throws.
- Existing row/col/diag/rev-diag win tests still pass.
