# Order status: State pattern or not?

## Short answer
Not the full GoF State pattern. The states differ only in *which transitions are allowed*; they do not have different behavior for the same operation (no state where "cook" does something different, just allowed or not). A State class per status would be six near-empty classes each repeating "throw IllegalTransition" for most methods. Use an **enum with a transition table**, plus the **Observer** pattern for notifications, since notification is the part that actually varies and grows (analytics later).

Switch to State classes if per-state behavior appears, e.g. cancellation from COOKING triggers a partial refund and restaurant compensation while cancellation from PLACED is free, and that logic grows.

## Design

```java
public enum OrderStatus {
    PLACED, CONFIRMED, COOKING, PICKED, DELIVERED, CANCELLED;

    private static final Map<OrderStatus, Set<OrderStatus>> ALLOWED = new EnumMap<>(OrderStatus.class);
    static {
        ALLOWED.put(PLACED,    EnumSet.of(CONFIRMED, CANCELLED));
        ALLOWED.put(CONFIRMED, EnumSet.of(COOKING, CANCELLED));
        ALLOWED.put(COOKING,   EnumSet.of(PICKED, CANCELLED));
        ALLOWED.put(PICKED,    EnumSet.of(DELIVERED));
        ALLOWED.put(DELIVERED, EnumSet.noneOf(OrderStatus.class));
        ALLOWED.put(CANCELLED, EnumSet.noneOf(OrderStatus.class));
    }

    public boolean canMoveTo(OrderStatus next) { return ALLOWED.get(this).contains(next); }
    public boolean isTerminal() { return ALLOWED.get(this).isEmpty(); }
}

public record OrderStatusChanged(String orderId, OrderStatus from, OrderStatus to, Instant at) {}

public interface OrderStatusListener {
    void onStatusChanged(OrderStatusChanged event);
}

public final class Order {
    private final String id;
    private OrderStatus status = OrderStatus.PLACED;

    Order(String id) { this.id = id; }

    /** Returns the event; the caller publishes it after the change is persisted. */
    synchronized OrderStatusChanged transitionTo(OrderStatus next, Clock clock) {
        if (!status.canMoveTo(next))
            throw new IllegalStateTransitionException(id, status, next);
        OrderStatus from = status;
        status = next;
        return new OrderStatusChanged(id, from, next, clock.instant());
    }
    public OrderStatus status() { return status; }
}

public final class OrderService {
    private final OrderRepository repo;
    private final List<OrderStatusListener> listeners;   // CustomerNotifier, RestaurantNotifier, later AnalyticsListener
    private final Clock clock;

    public void confirm(String id) { change(id, OrderStatus.CONFIRMED); }
    public void startCooking(String id) { change(id, OrderStatus.COOKING); }
    public void pickUp(String id) { change(id, OrderStatus.PICKED); }
    public void deliver(String id) { change(id, OrderStatus.DELIVERED); }
    public void cancel(String id) { change(id, OrderStatus.CANCELLED); }

    private void change(String id, OrderStatus next) {
        Order o = repo.get(id);
        OrderStatusChanged evt = o.transitionTo(next, clock);
        repo.save(o);                                   // optimistic version check in DB
        for (OrderStatusListener l : listeners) {
            try { l.onStatusChanged(evt); }
            catch (RuntimeException e) { log.warn("listener {} failed for {}", l, evt, e); }
        }
    }
}
```

Adding analytics = one new `OrderStatusListener` implementation registered in wiring. No change to `Order` or `OrderStatus`.

## Points worth calling out
- **Persist then notify.** Never notify for a transition that did not commit. In production, write the event to an outbox table in the same transaction as the status update and have a relay publish it (Kafka/SNS); customer/restaurant/analytics become consumers. The in-process listener list above is the single-service version of the same idea.
- **One listener failing must not block others or roll back the order.** Hence the try/catch; with the outbox, retries are the relay's job.
- **Concurrent transitions** (restaurant cancels while rider picks up): use an optimistic `version` column, so the loser gets a conflict and re-reads, instead of overwriting.
- Listeners should be idempotent on `(orderId, to)` since at-least-once delivery may repeat events.

## Tests
- Every allowed transition succeeds; parameterized test over all 36 (from, to) pairs asserting exactly the allowed set works.
- Cancel from PICKED / DELIVERED throws; nothing leaves CANCELLED or DELIVERED.
- Each successful change notifies all listeners once with correct from/to; a failed transition notifies nobody.
- A throwing listener does not stop the others and does not undo the change.
