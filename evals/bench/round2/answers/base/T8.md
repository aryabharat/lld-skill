# Refactor DiscountCalculator

## Problems with the current code
- Every new rule edits this method (weekly), so the class never closes and every change risks the others.
- No way to say "these don't stack".
- No record of which rules applied, so finance cannot audit.
- `double` for money: rounding errors (`0.1 * total`). Use `BigDecimal` (or long minor units).
- Coupon codes and amounts are hardcoded; marketing has to ship code to change "100 off".
- `o.coupon().equals(...)` repeated with null checks; `LocalDate.now()`-style hidden time dependencies are a risk for date rules.

## Assumptions
- Rules compute on the order's original total (not compounding on each other), as today.
- Non-stacking is expressed as **exclusivity groups**: within a group only the best (largest) applicable discount applies; rules in different groups stack. E.g. both coupons in group `COUPON`. If marketing needs "rule X excludes everything", that is a group `EXCLUSIVE` plus a policy flag (shown below).
- The 30% cap stays as a global policy, applied last, and is itself recorded.
- Rules are code (Strategy) for now; once the set stabilises, the common ones (percent off, flat off over threshold, coupon) become data-configured instances of a few generic classes so marketing does not need deploys.

## Design

```java
public interface DiscountRule {
    String id();                                     // stable id for audit, e.g. "PREMIUM_10PCT"
    Optional<String> exclusivityGroup();             // rules in the same group don't stack
    int priority();                                  // tie-break inside a group
    Optional<BigDecimal> evaluate(Order o);          // amount if applicable, else empty
}

public record AppliedDiscount(String ruleId, BigDecimal amount) {}

public record DiscountResult(BigDecimal total,
                             List<AppliedDiscount> applied,
                             List<String> suppressed,      // applicable but lost to a group rival
                             boolean capped) {}
```

Rules, one class each (or generic parameterised classes):

```java
final class PercentForPremium implements DiscountRule {
    public String id() { return "PREMIUM_10PCT"; }
    public Optional<String> exclusivityGroup() { return Optional.empty(); }
    public int priority() { return 0; }
    public Optional<BigDecimal> evaluate(Order o) {
        return o.user().isPremium() ? Optional.of(pct(o.total(), "0.10")) : Optional.empty();
    }
}

final class FlatOverThreshold implements DiscountRule {
    private final String id; private final BigDecimal threshold, amount;
    FlatOverThreshold(String id, BigDecimal threshold, BigDecimal amount) { ... }
    public Optional<BigDecimal> evaluate(Order o) {
        return o.total().compareTo(threshold) > 0 ? Optional.of(amount) : Optional.empty();
    }
    ...
}

final class CouponRule implements DiscountRule {
    private final String code;
    private final Predicate<Order> extraCondition;          // e.g. October only
    private final Function<Order, BigDecimal> amount;
    public Optional<String> exclusivityGroup() { return Optional.of("COUPON"); }
    public Optional<BigDecimal> evaluate(Order o) {
        return code.equals(o.coupon()) && extraCondition.test(o)   // null-safe: code is non-null
            ? Optional.of(amount.apply(o)) : Optional.empty();
    }
    ...
}

final class FirstOrder implements DiscountRule {
    public Optional<BigDecimal> evaluate(Order o) {
        return o.user().orders() == 0 ? Optional.of(new BigDecimal("25")) : Optional.empty();
    }
    ...
}
```

The calculator only orchestrates; it never changes when a rule is added:

```java
public final class DiscountCalculator {
    private final List<DiscountRule> rules;
    private final BigDecimal maxFraction;                    // 0.30

    public DiscountCalculator(List<DiscountRule> rules, BigDecimal maxFraction) {
        this.rules = List.copyOf(rules);
        this.maxFraction = maxFraction;
    }

    public DiscountResult calculate(Order o) {
        Map<String, List<AppliedDiscount>> byGroup = new LinkedHashMap<>();
        List<AppliedDiscount> stackable = new ArrayList<>();

        for (DiscountRule r : rules) {
            r.evaluate(o).filter(a -> a.signum() > 0).ifPresent(a -> {
                AppliedDiscount d = new AppliedDiscount(r.id(), a);
                r.exclusivityGroup().ifPresentOrElse(
                    g -> byGroup.computeIfAbsent(g, k -> new ArrayList<>()).add(d),
                    () -> stackable.add(d));
            });
        }

        List<AppliedDiscount> applied = new ArrayList<>(stackable);
        List<String> suppressed = new ArrayList<>();
        for (List<AppliedDiscount> group : byGroup.values()) {
            AppliedDiscount best = group.stream()
                .max(Comparator.comparing(AppliedDiscount::amount)).orElseThrow();
            applied.add(best);
            group.stream().filter(d -> d != best).forEach(d -> suppressed.add(d.ruleId()));
        }

        BigDecimal sum = applied.stream().map(AppliedDiscount::amount)
                                .reduce(BigDecimal.ZERO, BigDecimal::add);
        BigDecimal cap = o.total().multiply(maxFraction).setScale(2, RoundingMode.HALF_UP);
        boolean capped = sum.compareTo(cap) > 0;
        return new DiscountResult(capped ? cap : sum, List.copyOf(applied), List.copyOf(suppressed), capped);
    }
}
```

Wiring (Spring would inject `List<DiscountRule>`; or a registry built from config):

```java
new DiscountCalculator(List.of(

    new FirstOrder()
), new BigDecimal("0.30"));
```

## Finance audit
`DiscountResult.applied` (rule id + amount), `suppressed`, and `capped` are persisted with the order (an `order_discounts` table: `order_id, rule_id, amount, status [APPLIED|SUPPRESSED]`, plus a `capped` flag on the order). When the cap kicks in, decide with finance how to attribute the reduction: proportional across applied rules is the usual answer, so line amounts sum to the order's discount. Rule ids must be stable and never reused; version them (`FESTIVE_2026`) when the terms change.

## Behaviour change to flag
In the current code `WELCOME` and `FESTIVE` cannot both apply anyway (one coupon field), so grouping coupons changes nothing today. Every other rule still stacks as before, and the cap is unchanged, so outputs for existing orders are identical except for `double` vs `BigDecimal` rounding. I would land this refactor first with characterization tests proving equal results, then add exclusivity groups as marketing requests them.

## Tests
- Characterization: a table of orders (premium/not, total around 1000, each coupon, October/not, first order/not) asserting the same discount as the old method (to the cent).
- Each rule in isolation: applies / does not apply at boundaries (total exactly 1000 does not get 50; FESTIVE in September does not apply; null coupon is safe).
- Exclusivity: two rules in one group -> only the larger applied, the other in `suppressed`; rules in different groups stack.
- Cap: sum above 30% -> result equals cap, `capped=true`, applied list still lists all contributing rules.
- Adding a new rule requires no change to `DiscountCalculator` (test with a stub rule).
- Determinism: rule order in the list does not change the result.
