# Builder for `Point(x, y)`? No.

Builder pays off when an object has many parameters, several of them optional, or same-typed parameters that are easy to swap, or when construction needs staged validation. `Point` has two required fields and no optional ones. A builder would add a second class, make construction more verbose (`Point.builder().x(1).y(2).build()` vs `new Point(1, 2)`), and make it possible to forget `y` at compile time, which the constructor makes impossible.

Use a record (Java 16+):

```java
public record Point(int x, int y) {
    public static final Point ORIGIN = new Point(0, 0);

    public Point translate(int dx, int dy) { return new Point(x + dx, y + dy); }
}
```

You get immutability, `equals`/`hashCode`/`toString`, and a clear constructor for free. If you need validation, add a compact constructor. If you want named construction for readability, add static factories such as `Point.of(x, y)` or `Point.polar(r, theta)`; those also solve the "which argument is which" concern better than a builder.

The x/y swap risk is the one real argument for a builder here, and it is weak: `(x, y)` is a universal convention. If it were something like `Range(int start, int endExclusive, int step, boolean inclusive, ...)` growing to 5+ fields, revisit.
