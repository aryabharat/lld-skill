# Review: NotificationService

Request changes. The throttle is not thread-safe, which on request threads is a real bug, and there are a few design and test issues.

## Blocking

1. **`HashMap` shared across request threads.** `lastSent` is a `static HashMap` mutated from many threads. Concurrent `put`s can corrupt the map (lost entries, and on older JDKs infinite loops during resize), and reads have no visibility guarantee. At minimum use `ConcurrentHashMap`.

2. **Check-then-act race.** Even with `ConcurrentHashMap`, `getOrDefault` ... `send` ... `put` is not atomic. Two requests for the same user arriving together both pass the check and both send. The throttle must be claimed atomically *before* sending:
   ```java
   boolean tryAcquire(String key) {
       long now = clock.millis();
       boolean[] acquired = {false};
       lastSent.compute(key, (k, prev) -> {
           if (prev == null || now - prev >= windowMs) { acquired[0] = true; return now; }
           return prev;
       });
       return acquired[0];
   }
   ```

3. **Unbounded memory growth.** One entry per user forever, `static`, never evicted. Over time this is a leak. Use a cache with expire-after-write = window (Caffeine), or periodically purge entries older than the window.

4. **`static` state.** Makes the throttle global across instances, leaks between tests (the provided test will pass or fail depending on test order), and cannot be reset. Make it an instance field injected via constructor.

## Correctness / behaviour questions

5. **Shared key across channels.** All three methods use the same `userId` key, so an email suppresses the SMS and push for 60 s. If that is intended ("one notification per user per minute"), document it; I suspect it is not, especially for something like an OTP SMS after a marketing email. Key by `(userId, channel)` unless product says otherwise.

6. **Silent drop.** `return` with no log, metric, or return value. Callers cannot tell a throttled message from a sent one. Return a result (`SENT`, `THROTTLED`, `FAILED`) and emit a metric.

7. **Timestamp recorded after send, and send failures.** In the current code, if `send` throws, nothing is recorded (fine), but if a send is slow, concurrent requests all get through (race above). With the acquire-first approach, decide what happens on failure: release the slot (remove the entry if it still equals our timestamp, using `remove(key, now)`) so a retry is possible.

8. **Blocking I/O on request threads.** Each `send` is a network call made synchronously on the web request thread. Consider handing off to a queue/executor, with the throttle check done before enqueueing. At least set client timeouts.

9. **Single-instance only.** If the web tier has more than one instance, each has its own map and a user can get N messages per minute. If the limit matters across instances, move it to Redis (`SET key 1 NX PX 60000`), which is atomic and expires on its own.

## Design

10. **Triplicated code.** Three copies of the throttle logic. Extract a `Throttle` (or `RateLimiter`) and a `NotificationChannel` interface:
    ```java
    interface NotificationChannel { Channel type(); void send(User u, String msg); }

    public final class NotificationService {
        private final Map<Channel, NotificationChannel> channels;
        private final Throttle throttle;

        public SendResult send(Channel ch, User u, String msg) {
            String key = u.getId() + ":" + ch;
            if (!throttle.tryAcquire(key)) { metrics.throttled(ch); return SendResult.THROTTLED; }
            try { channels.get(ch).send(u, msg); return SendResult.SENT; }
            catch (RuntimeException e) { throttle.release(key); throw e; }
        }
    }
    ```
    Adding WhatsApp becomes a new channel class, not a fourth copy-paste.

11. **`System.currentTimeMillis()` is called twice and is not injectable.** Inject a `Clock` (or `LongSupplier`); use `nanoTime`-based or a monotonic source if wall-clock jumps matter. The 60_000 should be a named, configurable `Duration`.

12. Null handling: `u.getEmail()`, `getPhone()`, `getDeviceToken()` may be null for users without that channel; check and return a clear result.

## Tests

The existing test only checks the happy-path throttle and depends on static state and real time. Add:
- With a fake clock: second send at t+59,999 ms is throttled, at t+60,000 ms goes through (boundary).
- Different users are independent.
- Different channels are independent (or explicitly shared, whichever is decided).
- Send failure releases the slot so a retry goes through.
- Concurrency: 50 threads released by a `CountDownLatch` call `sendEmail` for the same user; assert exactly 1 send. This test fails against the current code.
- Test isolation: each test builds a new service (falls out of removing `static`).
