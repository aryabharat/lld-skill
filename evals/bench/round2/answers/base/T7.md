# Schema: organisations, members, repositories, teams, access

## Assumptions
- PostgreSQL. Surrogate `bigint` ids (identity), plus unique human-readable slugs.
- A repository is owned by exactly one organisation (personal repos out of scope; if needed, add `owner_user_id` with a check that exactly one owner is set).
- Teams belong to one organisation; only members of that org can be on its teams.
- Repository permission levels: `read < triage < write < maintain < admin`. Effective permission = max of direct user grant, grants via any team the user is in, and org-admin (implicitly admin on all org repos).
- Soft deletes not modeled; FK actions noted per table.

## Tables

```sql
CREATE TABLE users (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  login       citext NOT NULL UNIQUE,          -- case-insensitive unique handle
  email       citext NOT NULL UNIQUE,
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE organisations (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  login       citext NOT NULL UNIQUE,
  name        text NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TYPE org_role AS ENUM ('member', 'admin');

CREATE TABLE org_memberships (
  org_id      bigint NOT NULL REFERENCES organisations(id) ON DELETE CASCADE,
  user_id     bigint NOT NULL REFERENCES users(id)         ON DELETE CASCADE,
  role        org_role NOT NULL DEFAULT 'member',
  created_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (org_id, user_id)                -- one role per user per org
);
CREATE INDEX org_memberships_user_idx ON org_memberships (user_id);   -- "orgs I belong to"

CREATE TABLE repositories (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  org_id      bigint NOT NULL REFERENCES organisations(id) ON DELETE RESTRICT,
  name        citext NOT NULL,
  visibility  text NOT NULL CHECK (visibility IN ('public','private','internal')),
  created_at  timestamptz NOT NULL DEFAULT now(),
  UNIQUE (org_id, name),                       -- org/repo path is unique; also serves "repos of org"
  UNIQUE (id, org_id)                          -- target for composite FK below
);

CREATE TABLE teams (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  org_id      bigint NOT NULL REFERENCES organisations(id) ON DELETE CASCADE,
  slug        citext NOT NULL,
  name        text NOT NULL,
  UNIQUE (org_id, slug),
  UNIQUE (id, org_id)
);

CREATE TABLE team_members (
  team_id     bigint NOT NULL,
  org_id      bigint NOT NULL,
  user_id     bigint NOT NULL,
  PRIMARY KEY (team_id, user_id),
  FOREIGN KEY (team_id, org_id) REFERENCES teams(id, org_id) ON DELETE CASCADE,
  -- user must be a member of the team's org; removing org membership removes team membership
  FOREIGN KEY (org_id, user_id) REFERENCES org_memberships(org_id, user_id) ON DELETE CASCADE
);
CREATE INDEX team_members_user_idx ON team_members (user_id);           -- "teams I'm on"

CREATE TYPE repo_permission AS ENUM ('read', 'triage', 'write', 'maintain', 'admin');  -- ordered

CREATE TABLE repo_user_grants (
  repo_id     bigint NOT NULL REFERENCES repositories(id) ON DELETE CASCADE,
  user_id     bigint NOT NULL REFERENCES users(id)        ON DELETE CASCADE,
  permission  repo_permission NOT NULL,
  granted_by  bigint REFERENCES users(id) ON DELETE SET NULL,
  created_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (repo_id, user_id)
);
CREATE INDEX repo_user_grants_user_idx ON repo_user_grants (user_id);  -- "repos I can access directly"

CREATE TABLE repo_team_grants (
  repo_id     bigint NOT NULL,
  team_id     bigint NOT NULL,
  org_id      bigint NOT NULL,
  permission  repo_permission NOT NULL,
  granted_by  bigint REFERENCES users(id) ON DELETE SET NULL,
  created_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (repo_id, team_id),
  -- team and repo must be in the same org
  FOREIGN KEY (repo_id, org_id) REFERENCES repositories(id, org_id) ON DELETE CASCADE,
  FOREIGN KEY (team_id, org_id) REFERENCES teams(id, org_id)        ON DELETE CASCADE
);
CREATE INDEX repo_team_grants_team_idx ON repo_team_grants (team_id);   -- "repos this team can access"
```

## Why two grant tables instead of one polymorphic table
A single `repo_grants(repo_id, grantee_type, grantee_id)` cannot have a real foreign key on `grantee_id`, so deleting a team leaves orphan grants and nothing enforces that the grantee exists. Two tables keep FKs and cascades honest. The alternative that keeps one table is `user_id NULL, team_id NULL` with `CHECK (num_nonnulls(user_id, team_id) = 1)` and two partial unique indexes; acceptable, but two tables are simpler to query and index.

## Why the composite `(id, org_id)` keys
They let the database enforce cross-table invariants that otherwise live only in application code and drift: a team grant can only reference a repo and team in the same org, and a team member must be an org member. `UNIQUE (id, org_id)` is redundant for uniqueness but required as an FK target.

## The hot query: "what permission does user U have on repo R?"

```sql
SELECT max(p) FROM (
  SELECT 'admin'::repo_permission AS p
    FROM repositories r JOIN org_memberships m ON m.org_id = r.org_id
   WHERE r.id = :repo AND m.user_id = :user AND m.role = 'admin'
  UNION ALL
  SELECT g.permission FROM repo_user_grants g
   WHERE g.repo_id = :repo AND g.user_id = :user
  UNION ALL
  SELECT g.permission FROM repo_team_grants g
    JOIN team_members tm ON tm.team_id = g.team_id
   WHERE g.repo_id = :repo AND tm.user_id = :user
) x;
```

Index use: `repositories` PK; `org_memberships` PK `(org_id, user_id)`; `repo_user_grants` PK `(repo_id, user_id)`; `repo_team_grants` PK prefix `repo_id` then `team_members` PK `(team_id, user_id)`. Every branch is index-only or close to it. Postgres enums compare by declaration order, so `max` works on `repo_permission`. Plus public-repo read access in the application (or a fourth branch on `visibility`).

## Index summary and reasons
| Index | Serves |
|---|---|
| `org_memberships PK (org_id, user_id)` | list org members; membership/role check |
| `org_memberships (user_id)` | list a user's orgs (PK leads with org_id, so needed) |
| `repositories UNIQUE (org_id, name)` | resolve `org/repo` URL; list org's repos |
| `teams UNIQUE (org_id, slug)` | resolve team URL; list org's teams |
| `team_members PK (team_id, user_id)` | list team members; permission check join |
| `team_members (user_id)` | user's teams; "repos I can access" via teams |
| `repo_user_grants PK (repo_id, user_id)` | permission check; list collaborators of a repo |
| `repo_user_grants (user_id)` | repos a user was granted directly |
| `repo_team_grants PK (repo_id, team_id)` | permission check; list teams on a repo |
| `repo_team_grants (team_id)` | team's repos; cascade delete of a team without seq scan |

I would not add more until query plans demand them. Every FK column that is not the leading column of some index got its own index, because Postgres does not index FKs automatically and cascading deletes on large child tables would otherwise seq-scan.

## Scale notes
- "List all repos user U can see" is the expensive query (union over direct grants, team grants, org-admin orgs). If it becomes hot, maintain a denormalised `repo_access(user_id, repo_id, permission)` table updated on grant/membership changes (or a materialised view refreshed incrementally), with PK `(user_id, repo_id)`. Do this only when needed; it adds write amplification when a large team gains access.
- Audit: grant changes usually need history; add an append-only `access_audit_log` rather than relying on `created_at`.
