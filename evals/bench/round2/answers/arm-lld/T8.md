# Refactor: DiscountCalculator

## The smell

Every marketing request edits the same `if` chain, so the most-changed method is also the riskiest. There are two more problems the new requirements expose:
- The method returns a bare `double`, so finance cannot see which rules applied.
- Money is held in `double`, which gives sums like 0.1 + 0.2 = 0.30000000000000004.

With a new rule every week, the evidence for an extension point is already here. So I'd make each condition a rule object, resolve stacking and the cap in one place, and return an itemised result.

## Before touching it

I'd pin the current behaviour with characterization tests: premium alone, total > 1000, WELCOME, FESTIVE in October and in November, first order, and a stack that hits the 30% cap. The refactor must keep them green. The one exception is rounding, now that the code uses paise.

## After

```java
record Money(long paise) {                                     // integer minor units, no double
  Money percent(int bps) { return new Money((paise * bps + 5_000) / 10_000); }   // half-up
  Money plus(Money o) { return new Money(paise + o.paise); }
  boolean gt(Money o) { return paise > o.paise; }
}

record AppliedDiscount(String ruleId, Money amount, Status status) {
  enum Status { APPLIED, SUPPRESSED_BY_STACKING, CAPPED }
}
record DiscountResult(Money total, List<AppliedDiscount> lines) {}   // finance gets every line

interface DiscountRule {
  String id();                                     // stable, stored with the order
  Optional<String> exclusiveGroup();               // rules in one group never stack
  Optional<Money> evaluate(Order o);               // empty = does not apply
}

final class PremiumDiscount implements DiscountRule {
  public String id() { return "PREMIUM_10"; }
  public Optional<String> exclusiveGroup() { return Optional.empty(); }
  public Optional<Money> evaluate(Order o) {
    return o.user().isPremium() ? Optional.of(o.total().percent(1_000)) : Optional.empty();
  }
}

final class CouponDiscount implements DiscountRule {          // WELCOME and FESTIVE are two instances
  private final String code; private final Predicate<Order> when; private final Function<Order, Money> amount;
  public String id() { return "COUPON_" + code; }
  public Optional<String> exclusiveGroup() { return Optional.of("COUPON"); }
  public Optional<Money> evaluate(Order o) {
    return code.equals(o.coupon()) && when.test(o) ? Optional.of(amount.apply(o)) : Optional.empty();
  }
}
// HighValueFlat50, FirstOrderFlat25 follow the same shape.

final class DiscountCalculator {
  private final List<DiscountRule> rules;          // injected; a new rule is a new class + registration
  private final int capBps;                        // 3000 = 30%

  DiscountResult discount(Order o) {
    List<AppliedDiscount> lines = new ArrayList<>();
    Map<String, AppliedDiscount> bestInGroup = new LinkedHashMap<>();
    for (DiscountRule r : rules) {
      Optional<Money> amt = r.evaluate(o);         // every rule reads the order, never another rule
      if (amt.isEmpty()) continue;
      AppliedDiscount d = new AppliedDiscount(r.id(), amt.get(), APPLIED);
      if (r.exclusiveGroup().isEmpty()) { lines.add(d); continue; }
      bestInGroup.merge(r.exclusiveGroup().get(), d, (kept, cand) -> {
        boolean candWins = cand.amount().gt(kept.amount());   // ties: first registered wins
        lines.add(suppressed(candWins ? kept : cand));
        return candWins ? cand : kept;
      });
    }
    lines.addAll(bestInGroup.values());

    Money sum = lines.stream().filter(l -> l.status() == APPLIED)
                     .map(AppliedDiscount::amount).reduce(new Money(0), Money::plus);
    Money cap = o.total().percent(capBps);
    if (sum.gt(cap)) {
      lines.add(new AppliedDiscount("CAP_30_PCT", new Money(cap.paise() - sum.paise()), CAPPED));
      return new DiscountResult(cap, List.copyOf(lines));
    }
    return new DiscountResult(sum, List.copyOf(lines));
  }
  private static AppliedDiscount suppressed(AppliedDiscount d) {
    return new AppliedDiscount(d.ruleId(), d.amount(), SUPPRESSED_BY_STACKING);
  }
}
```

## Decisions behind it

1. **Rule list, not if-chain.** Each rule computes from the order alone, never from the running discount. That keeps them order-free, so a list is safe. Adding a rule means a new class plus one registration line, and `DiscountCalculator` stays untouched and tested. Stacking is data (`exclusiveGroup`), resolved in one place. The policy is "best in group wins", and it is written down and tested.
2. **The result is itemised.** The lines show what applied, what qualified but lost on stacking, and the cap adjustment. Persist them as `order_discounts(order_id, rule_id, amount_paise, status)` in the same transaction as the order. Finance then gets an answer per order, and support can say why a coupon didn't apply.
3. **Money is in paise with a stated rounding rule** (half-up, per line). The order date stays on the order (`o.date()`), never the system clock.

## Rejected

- **Chain of Responsibility:** this is not first-match, because every qualifying rule contributes.
- **Wrapping the calculator in decorators per rule:** that builds an onion whose order nobody can see.
- **Rules as JSON in a DB with an admin UI:** that is the next step if marketing wants to self-serve without a deploy. It adds a type registry, schema versioning, and indexed validity columns. With engineers shipping one rule a week, rule classes in code give most of the benefit.

## Watch out

If marketing asks for "10% off after other discounts", the rules are no longer order-free. Then add explicit phases (flat first, then percentage on the remainder), with the phase order pinned by a test. Do not quietly depend on list order.

## Tests

- Each rule, table-driven:
  - FESTIVE in October gives 10000 paise; in November, nothing.
  - WELCOME on 2000.00 gives 100.00.
- **Stacking:** WELCOME (5%) and a new 8% coupon in group COUPON on 1000.00. Only the 80.00 coupon is APPLIED; WELCOME is SUPPRESSED_BY_STACKING with 50.00.
- **Cap, with exact numbers:**
  - A premium first-time user with WELCOME on 1200.00: 120 + 50 + 60 + 25 = 255.00. That is under the cap of 360.00, so there is no CAPPED line.
  - The same user on 100.00: 10 + 5 + 25 = 40.00. The cap is 30.00, so the total is 30.00, with a CAPPED line of -10.00.
- **Adding a new rule class** needs no change to `DiscountCalculator` or its tests.
- **The characterization suite** stays green.
