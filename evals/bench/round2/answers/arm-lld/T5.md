# Review: NotificationService throttling

**What this change does:** it sends email, SMS or push, and drops a message when the same user got any message in the last 60 seconds. The "last sent" times live in a static `HashMap` keyed by user id.

**Load assumed:** many request threads in one JVM, and possibly several instances behind a load balancer.

## Must fix

**1. Unsynchronised static `HashMap` shared by request threads** (`lastSent`, every `get`/`put`)
- **Problem:** `HashMap` is not thread-safe. Concurrent `put`s during a resize can lose entries or corrupt the bucket structure, and reads can see a half-written map. Throttling then fails silently, or a `get` misbehaves under load.
- **Fix:** use a `ConcurrentHashMap` owned by an injected throttle object (see 2).
- **Rule:** shared mutable state needs a named mechanism.

**2. Check-then-act race lets duplicates through** (lines 1-3 of each method)
- **Problem:** two requests for user U arrive together. Both read "no send in 60 s", both call `send`, and U gets two messages. The window is wide, because `send` is a network call and the timestamp is only written after it returns. Every request that arrives during a slow send passes the check. A `ConcurrentHashMap` alone does not fix this: the race is in the sequence of calls, not in any single call.
- **Fix:** reserve the slot atomically before sending, and give it back if the send fails.
  ```java
  final class Throttle {
    private final ConcurrentHashMap<String, Long> last = new ConcurrentHashMap<>();
    private final long windowMs;
    boolean tryAcquire(String key, long now) {
      boolean[] won = {false};
      last.compute(key, (k, prev) -> {
        if (prev != null && now - prev < windowMs) return prev;   // still throttled
        won[0] = true; return now;                                // reserve
      });
      return won[0];
    }
    void release(String key, long reservedAt) { last.remove(key, reservedAt); } // only our reservation
  }
  ```
- **Rule:** check-then-act must be one atomic step.

**3. Unbounded memory growth** (`lastSent`)
- **Problem:** every user who has ever been notified stays in the map forever. On a service with millions of users, this is a leak that grows until restart.
- **Fix:** drop entries older than the window. Use a cache with `expireAfterWrite(60s)` (Caffeine; its `asMap().compute` keeps fix 2 atomic), or run a scheduled sweep that removes entries with `now - ts >= windowMs`.
- **Rule:** structures keyed by an unbounded id need eviction.

**4. One throttle key for all channels drops messages across channels** (the shared `u.getId()` key)
- **Problem:** a welcome email at t=0 silently drops an OTP SMS at t=10s. All three methods share a key, so any message on any channel blocks the others. If a global per-user limit was intended, it needs a stated product decision and an exemption for transactional messages. If not, this loses messages.
- **Fix:** key by `userId + ":" + channel`, or confirm the global limit and say so in the method's contract.
- **Rule:** names and contracts must not lie (`sendSms` that may not send).

## Should fix

**5. Throttled sends are invisible to the caller** (`return;`)
- **Problem:** `void` plus a silent return means the caller cannot log it, retry it, or show "try again in a minute". Tests can only check the fake's list.
- **Fix:** return `SendResult { SENT, THROTTLED }`, or a future of it (see 7).
- **Rule:** use a result object when there are more than two outcomes, or when the caller must react.

**6. System clock read in logic, twice per call** (`System.currentTimeMillis()` x2)
- **Problem:** the check and the stamp use different instants. Window expiry cannot be tested without `Thread.sleep(60_000)`, so it isn't tested.
- **Fix:** inject a `Clock`, read it once per call into `now`, and use that value for both the check and the reservation.
- **Rule:** inject time and read it once per operation.

**7. Blocking network IO on request threads** (`emailClient.send`, `smsClient.send`, `pushClient.send`)
- **Problem:** a slow SMS gateway (2 s) ties up a request thread per notification. A burst can drain the server's pool, and fast requests queue behind slow ones.
- **Fix:** have the channel return a `CompletableFuture`, run it on a bounded executor, and release the reservation on both kinds of failure:
  ```java
  CompletableFuture<SendResult> send(User u, Channel ch, String msg) {
    long now = clock.millis(); String key = u.getId() + ":" + ch.name();
    if (!throttle.tryAcquire(key, now)) return completedFuture(SendResult.THROTTLED);
    CompletableFuture<Void> f;
    try { f = ch.send(u, msg); }                                         // may throw synchronously
    catch (RuntimeException e) { throttle.release(key, now); return failedFuture(e); }
    return f.handle((v, e) -> {
      if (e != null) { throttle.release(key, now); throw new CompletionException(e); }
      return SendResult.SENT;
    });
  }
  ```
  This changes the return type from `void`. Callers that cannot handle a future yet can keep the old methods as thin wrappers that discard the result, while they migrate.
- **Rule:** request threads never block on IO.

**8. Three copies of the same method** (`sendEmail` / `sendSms` / `sendPush`)
- **Problem:** the throttle logic is pasted three times. Fixes 2, 3 and 6 must each be applied three times, and a fourth channel (WhatsApp) copies it again.
- **Fix:** add `interface Channel { String name(); CompletableFuture<Void> send(User u, String msg); }` with one implementation per client, each of which knows its own address field. One `send(User, Channel, String)` method holds the throttle. The old method names can delegate.
- **Rule:** duplicated methods that differ only by a collaborator should be one method plus a strategy.

**9. `static` state leaks between instances and tests** (`private static Map`)
- **Problem:** every `NotificationService` and every test shares the map. A later test that emails `user` within 60 s of `throttles()` gets silently throttled, so test results depend on run order.
- **Fix:** make it an instance field on an injected `Throttle`, built fresh per test.

**10. In-memory throttle per instance**
- **Problem:** with N instances, a user can get N messages per minute.
- **Fix:** if the limit matters across instances, back `Throttle` with a shared store (Redis `SET key NX PX 60000`). Otherwise, document that the limit is per instance.

## Nice to have

- **11.** The test covers only one case. Add: a send after the window with a fake clock (59 999 ms throttled, 60 000 ms sent), cross-channel behaviour per the decision in 4, a failed send that frees the slot, and N concurrent sends for one user that deliver exactly one message (latch-started threads).
- **12.** Make the magic `60_000` a constructor-injected `Duration window`.

## Verdict

Ship after the must-fixes (1-4). Items 5-9 belong in the same PR, because they touch the same lines.

## Skipped on purpose

I didn't suggest a pluggable limiter algorithm, because there is one fixed rule. I also didn't suggest retries or a DLQ for failed sends, because they are outside this diff.

## Not checked

The callers. Whether any caller relies on the silent drop, or on the shared cross-channel throttle, decides the final form of 4 and 5.
