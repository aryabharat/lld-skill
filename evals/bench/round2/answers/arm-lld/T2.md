# Draw after 50 moves without a win

I'd make the smallest change that fits: the board counts the moves it has accepted, and the engine adds one more draw check. It goes after the win checks and before (or beside) the full-board check.

```java
class Board {
  private int moveCount;                       // only accepted moves count

  void move(Move m) {
    validate(m);                               // occupied / out of range / wrong turn throw first
    place(m);
    moveCount++;
    lastPlayer = m.player();
  }
  int moveCount() { return moveCount; }
}

class GameEngine {
  static final int DEFAULT_MOVE_LIMIT = 50;
  private final int moveLimit;

  GameEngine()              { this(DEFAULT_MOVE_LIMIT); }
  GameEngine(int moveLimit) {
    if (moveLimit <= 0) throw new IllegalArgumentException("moveLimit must be > 0: " + moveLimit);
    this.moveLimit = moveLimit;
  }

  GameState getState(Board b) {
    if (rowWin(b))     return GameState.win(b.lastPlayer());
    if (colWin(b))     return GameState.win(b.lastPlayer());
    if (diagWin(b))    return GameState.win(b.lastPlayer());
    if (revDiagWin(b)) return GameState.win(b.lastPlayer());
    if (b.isFull())                   return GameState.draw();
    if (b.moveCount() >= moveLimit)   return GameState.draw();   // new
    return GameState.inProgress();
  }
}
```

## The decisions behind it

1. **Where the check sits.** It goes after every win check. A win on the 50th move is a win, not a draw. With the order shown, "without a win" is true by construction.
2. **Who owns the count.** The board already knows the last player, so it is the one place that sees every accepted move. Counting there means a rejected move (occupied cell) never moves the counter. Deriving the count from filled cells would also work for tic-tac-toe, but it breaks for any game with captures or removals. An explicit counter is honest for both.
3. **The limit is a constructor argument, with 50 as the default.** That avoids a magic number in the chain and lets tests use a small limit. It also lets another game mode pick its own limit without a subclass.

Note that on a 3x3 board `isFull()` fires at 9 moves, so this rule only matters on boards with 50 or more cells. If that is not the intended game, the requirement needs a second look.

If the game can be replayed or undone, every path that changes the board must keep `moveCount` in step (undo decrements it, loading from storage restores it).

## Tests

```java
@Test void drawAfterLimitWithoutWin() {           // limit 4 on a 5x5 board keeps it hand-checkable
  Board b = play(5, cells(0,0), cells(0,1), cells(1,2), cells(2,4));   // no line
  assertEquals(GameState.draw(), new GameEngine(4).getState(b));
```

## Refactor I am deferring

`getState` now has six `if ... return` lines, and two of them are draw rules. I would not build a rule engine for one new rule. If a third end-of-game rule arrives (time limit, threefold repetition, resignation), I'd turn each check into a `Rule` returning `Optional<GameState>` in an ordered list, with the win rules first and the draw rules last, so new rules are additions rather than edits to this method.
