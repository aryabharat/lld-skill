# Schema: organisations, members, teams, repositories, access grants

## Assumptions

- PostgreSQL. IDs are `bigint GENERATED ALWAYS AS IDENTITY`. Logins and slugs are case-insensitive unique handles (`citext`).
- Roles in an org are MEMBER or ADMIN. Repository permissions form an ordered ladder: READ(1) < TRIAGE(2) < WRITE(3) < MAINTAIN(4) < ADMIN(5). They are stored as `smallint` so "effective permission" is a `max()`.
- Org admins have ADMIN on every repo in the org.
- Direct user grants may go to people outside the org ("outside collaborators"). Teams contain only org members.
- Deferred: nested teams, user-owned repos, an org-wide default permission (it would be one nullable column on `organizations`), and audit history of grant changes.

## Queries that drive the shape

1. Is user U a member/admin of org O?
2. Which orgs does U belong to?
3. What is U's effective permission on repo R? This runs on every git push and every page view, so it is the hottest query.
4. List the repos of org O. List the repos U can access.
5. Who has access to repo R (the settings page)?
6. List the members of team T. List the teams U is in.

## Tables

```sql
CREATE TABLE users (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  login       citext NOT NULL UNIQUE,
  email       citext NOT NULL UNIQUE,
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE organizations (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  login       citext NOT NULL UNIQUE,
  name        text NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE org_memberships (
  org_id      bigint NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
  user_id     bigint NOT NULL REFERENCES users(id)         ON DELETE CASCADE,
  role        text   NOT NULL CHECK (role IN ('MEMBER','ADMIN')),
  created_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (org_id, user_id)                       -- Q1, and lists members of O
);
CREATE INDEX org_memberships_user ON org_memberships (user_id);                       -- Q2
CREATE INDEX org_memberships_admins ON org_memberships (org_id) WHERE role = 'ADMIN'; -- admin checks/lists

CREATE TABLE repositories (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  org_id      bigint NOT NULL REFERENCES organizations(id) ON DELETE RESTRICT,
  name        citext NOT NULL,
  visibility  text   NOT NULL CHECK (visibility IN ('PUBLIC','PRIVATE','INTERNAL')),
  created_at  timestamptz NOT NULL DEFAULT now(),
  UNIQUE (org_id, name),                              -- "acme/api" lookup, Q4 by org
  UNIQUE (org_id, id)                                 -- target for composite FKs below
);

CREATE TABLE teams (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  org_id      bigint NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
  slug        citext NOT NULL,
  name        text   NOT NULL,
  UNIQUE (org_id, slug),
  UNIQUE (org_id, id)
);

CREATE TABLE team_members (
  org_id      bigint NOT NULL,
  team_id     bigint NOT NULL,
  user_id     bigint NOT NULL,
  PRIMARY KEY (team_id, user_id),                     -- Q6 members of T
  FOREIGN KEY (org_id, team_id) REFERENCES teams (org_id, id)                      ON DELETE CASCADE,
  FOREIGN KEY (org_id, user_id) REFERENCES org_memberships (org_id, user_id)       ON DELETE CASCADE
);
CREATE INDEX team_members_user ON team_members (user_id, team_id);                -- Q3, Q6 teams of U

CREATE TABLE repo_user_grants (
  repo_id     bigint   NOT NULL REFERENCES repositories(id) ON DELETE CASCADE,
  user_id     bigint   NOT NULL REFERENCES users(id)        ON DELETE CASCADE,
  permission  smallint NOT NULL CHECK (permission BETWEEN 1 AND 5),
  granted_by  bigint   REFERENCES users(id) ON DELETE SET NULL,
  granted_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (repo_id, user_id)                      -- Q3 direct grant, Q5
);
CREATE INDEX repo_user_grants_user ON repo_user_grants (user_id);                 -- Q4 repos U can access

CREATE TABLE repo_team_grants (
  org_id      bigint   NOT NULL,
  repo_id     bigint   NOT NULL,
  team_id     bigint   NOT NULL,
  permission  smallint NOT NULL CHECK (permission BETWEEN 1 AND 5),
  granted_by  bigint   REFERENCES users(id) ON DELETE SET NULL,
  granted_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (repo_id, team_id),                     -- Q5 teams on R
  FOREIGN KEY (org_id, repo_id) REFERENCES repositories (org_id, id) ON DELETE CASCADE,
  FOREIGN KEY (org_id, team_id) REFERENCES teams (org_id, id)        ON DELETE CASCADE
);
CREATE INDEX repo_team_grants_team ON repo_team_grants (team_id, repo_id, permission); -- Q3, Q4
```

## Why it looks like this

- **Membership is a junction table, not a list column on the org.** Checking one membership becomes an index seek instead of reading and parsing every member. Adding a member is an insert, not a rewrite of a hot row. The role lives on the relationship, because the same user can be ADMIN in one org and MEMBER in another. The primary key `(org_id, user_id)` serves "is U in O"; the `user_id` index serves "my orgs".
- **Grants have two tables instead of one polymorphic `(grantee_type, grantee_id)` table.** A polymorphic id cannot carry a foreign key, so deleting a team would leave orphaned grants. With two tables, every reference is a real FK with a deliberate `ON DELETE`.
- **Composite FKs keep everything inside one org.** `(org_id, team_id)` and `(org_id, repo_id)` make it impossible to grant acme's team access to globex's repo. The FK from `team_members (org_id, user_id)` to `org_memberships` means only org members can be on a team. Removing someone from the org cascades them out of all its teams, and so out of every team-based grant, with no cleanup job.
- **`ON DELETE` choices:**
  - Deleting a user removes their memberships and grants (CASCADE).
  - `granted_by` is audit data, so it becomes NULL rather than blocking the user's deletion.
  - Deleting an org is RESTRICTed while repositories exist. Repositories are deleted (or archived) on purpose by a job, not as a side effect of an org-row delete.
  - Deleting a team cascades to its members and grants.
- **Permission as an ordered `smallint`** makes "best of direct grant, team grants and admin role" a `max()`. Use an enum in application code and map it at the DAO.

## The hot query (Q3)

```sql
SELECT max(p) AS permission FROM (
  SELECT 5 AS p
    FROM repositories r
    JOIN org_memberships m ON m.org_id = r.org_id AND m.user_id = :u AND m.role = 'ADMIN'
   WHERE r.id = :r
  UNION ALL
  SELECT permission FROM repo_user_grants WHERE repo_id = :r AND user_id = :u
  UNION ALL
  SELECT g.permission
    FROM team_members tm
    JOIN repo_team_grants g ON g.team_id = tm.team_id AND g.repo_id = :r
   WHERE tm.user_id = :u
) x;
```

Each branch is an index seek:
- **Admin branch:** the `repositories` PK, then the `org_memberships` PK.
- **Direct branch:** the `repo_user_grants` PK.
- **Team branch:** `team_members_user` gives U's handful of teams, then the PK `(repo_id, team_id)` of `repo_team_grants`.

A NULL result means no access, unless the repo is PUBLIC (READ). Q4 "repos U can access" is the same three sources driven from the user side, which is why `repo_user_grants_user` and `repo_team_grants_team` exist.

Every index above is justified by one of Q1-Q6. I added none for "maybe later". The admin partial index is small, and it keeps "list admins" and "is there another admin" cheap.

## Invariants enforced outside the schema

- **An org always keeps at least one admin.** A row constraint cannot express this. The service checks it when demoting or removing an admin, inside a transaction that first takes `SELECT ... FROM organizations WHERE id = :o FOR UPDATE`. Without that lock, two admins could demote each other concurrently.
- **Authorisation of changes:** only org admins, or users with ADMIN on the repo, may write `repo_*_grants`. This is checked in the owning service before the insert.

## Tests

- For each of Q1-Q6, run `EXPLAIN` on a seeded dataset and confirm an index scan, not a sequential scan.
- Granting org B's team access to org A's repo fails on the composite FK.
- Removing U from the org removes U's team memberships, and therefore U's access through those teams, but keeps U's direct outside-collaborator grants.
- Effective permission is the max of a direct READ and a team WRITE, which is WRITE. Org admin with no grants gets ADMIN.
- Deleting the user who granted access leaves the grant in place with `granted_by` NULL.
- Two concurrent "demote the other admin" transactions: exactly one succeeds.
