# Builder for `Point(x, y)`?

No. No pattern is needed here.

**Why:** Builder fixes one problem: many optional fields that would otherwise need a growing set of constructor overloads, or callers passing `null`/`0` placeholders. A point has two required fields, one obvious way to build it, and no defaults. A builder would add a class, a `build()` call people forget, and runtime checks for "x not set" that the compiler already gives you for free with a constructor.

**Use an immutable value type instead:**

```java
public record Point(int x, int y) {
  public static final Point ORIGIN = new Point(0, 0);
  public Point translate(int dx, int dy) { return new Point(x + dx, y + dy); }
}

Point p = new Point(3, 4);
```

`equals`, `hashCode` and `toString` come for free. Immutability also makes it safe to share across threads and to use as a map key.

**Rejected alternative:** a builder (`Point.builder().x(3).y(4).build()`). It is three times the code at every call site, adds a runtime failure mode, and solves nothing.

**What would flip the answer:** the point gains several optional fields with defaults (z, label, colour, precision, coordinate system), and the overloads start doubling. At that point, add a builder for those optional parts. If the pain is creation logic instead (for example, polar to Cartesian), use a named static factory such as `Point.polar(r, theta)`, not a builder.
