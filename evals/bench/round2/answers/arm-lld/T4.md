# Order status: State pattern?

**The problem in one line:** you need to stop illegal transitions (DELIVERED -> COOKING, cancelling after pickup) and fan each change out to a set of consumers that will grow.

**Pick:** a status enum that owns its allowed transitions, one `transitionTo` method on `Order`, an append-only status log, and Observer for the notifications. Not the State pattern, for now.

**Why not State:** the transition graph is small and sparse, which is the shape State fits. But the states have no behaviour of their own. Every state would hold only "which statuses may come next", and that is data. Six `OrderState` classes would each restate one line of the table below, and you would read six files to see the lifecycle. An enum keeps the whole graph in one screen. Notifications are not per-state behaviour either: every change notifies the same consumers.

**Why Observer:** customer and restaurant today, analytics later, so the set of consumers changes. With Observer, adding analytics is a new listener, and `Order` does not change. If it were only ever one fixed recipient, a direct call would do.

```java
enum OrderStatus {
  PLACED, CONFIRMED, COOKING, PICKED, DELIVERED, CANCELLED;
  private static final Map<OrderStatus, Set<OrderStatus>> NEXT = Map.of(
      PLACED,    EnumSet.of(CONFIRMED, CANCELLED),
      CONFIRMED, EnumSet.of(COOKING, CANCELLED),
      COOKING,   EnumSet.of(PICKED, CANCELLED),
      PICKED,    EnumSet.of(DELIVERED),
      DELIVERED, EnumSet.noneOf(OrderStatus.class),
      CANCELLED, EnumSet.noneOf(OrderStatus.class));
  boolean canMoveTo(OrderStatus to) { return NEXT.get(this).contains(to); }
}

interface OrderStatusListener { void onStatusChanged(StatusChanged e); }   // Customer, Restaurant, Analytics

final class OrderService {
  StatusChanged transition(OrderId id, OrderStatus to, Instant at) {
    StatusChanged e = repo.inTransaction(tx -> {
      Order o = tx.lockForUpdate(id);                       // one writer per order
      if (!o.status().canMoveTo(to))
        throw new IllegalTransition(id, o.status(), to);
      tx.updateStatus(id, to);
      tx.appendStatusLog(id, o.status(), to, at);           // history, same transaction
      return new StatusChanged(id, o.status(), to, at);
    });
    events.publish(e);                                      // only after commit
    return e;
  }
}
```

`events.publish` loops over the registered listeners and isolates each one in a try/catch, so a failing SMS gateway cannot block the restaurant notification. Across services, the publish becomes an outbox row written in the same transaction and relayed to a broker.

**Rejected:** the State pattern with one class per status. It makes sense when states start to behave differently. Example: cancelling from COOKING charges a fee and asks the restaurant to confirm, while cancelling from PLACED is a free instant refund. PICKED might also start a delivery timer that the other states don't have. When `transition` grows `if (status == COOKING)` branches for that kind of logic, move to State, with each class owning its own `cancel()` and `next()`.

**Watch out:**
- Status changes and notifications must not run in the opposite order. Publish only after the commit, or a listener will notify about a change that rolled back.
- Two concurrent requests (the restaurant confirms while the customer cancels) need the row lock or a conditional update (`WHERE status = :expected`). Otherwise both requests pass `canMoveTo`.
- Keep a single source of truth: the status column. The log is history, never a second state machine.
