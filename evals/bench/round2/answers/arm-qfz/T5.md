# T5 Review: NotificationService

Verdict: **request changes**. The throttle is not thread-safe, its scope is probably wrong, and the test cannot catch either problem.

## Blocking

**1. `static HashMap` mutated from request threads — data race.**
`HashMap` is not thread-safe. Concurrent `put`s from request threads can lose updates, and under resize can corrupt the table (lost entries, in old JDKs infinite loops on `get`). Every web request thread hits this map.

**2. Check-then-act race: the throttle does not throttle under concurrency.**
Even with a `ConcurrentHashMap`, `getOrDefault` ... `send` ... `put` is three separate steps. Two requests for the same user arriving together both read "not sent", both send, both write. The check and the "mark as sent" must be one atomic operation, done *before* the slow network call (the `send` can take hundreds of ms, which widens the window).

**3. One map shared by all three channels.**
`sendEmail` writes `lastSent[userId]`, so an SMS within the next 60 s is silently dropped. If the intent is "max one notification per user per minute across channels", say so in a name and a comment; I suspect it is not, because then "email + SMS for the same event" (common for OTP/security alerts) cannot work. Default I would expect: key by `(userId, channel)`.

**4. Messages are dropped silently.**
`return` with no log, metric or return value. The caller cannot tell "sent" from "throttled". For things like password-reset or OTP this is a user-visible bug. Return a result (`SENT` / `THROTTLED`) and count throttles in a metric. Also question whether *all* message types should be throttled — transactional messages usually should not be.

## Should fix

**5. Static mutable state.** `static` makes the map shared by every instance and every test. The test passes or fails depending on which tests ran before it with the same user id. Make it an instance field of an injected throttle component.

**6. Unbounded growth.** One entry per user forever — a slow memory leak on a long-running server. Entries older than the window are useless; evict them (Caffeine with `expireAfterWrite(window)`, or periodic cleanup).

**7. Time is not injectable.** `System.currentTimeMillis()` (called twice per send, with slightly different values) makes "after 60 s it sends again" untestable without sleeping. Inject a `Clock`.

**8. Duplicated logic x3.** The throttle is copy-pasted three times (that is how bug 3 got in unnoticed). Three identical copies is the point to extract it — one `Throttle` class, used by one send path.

**9. Ordering if send fails.** Today a failed `send` (exception) is not recorded, which is fine; after moving the reservation before the send (fix for #2), release the reservation on failure so a transient error does not block the user for a minute.

## Scope note
This throttle is per JVM. If the web tier runs N instances behind a load balancer, a user can get up to N messages per minute. If that matters, the same `Throttle` interface gets a Redis implementation (`SET key 1 NX PX 60000` — atomic). Not required to merge, but the class name/doc should say "per instance".

## The test
- Only covers email, same message twice, sequentially. It cannot detect #1/#2 (no concurrency), #3 (no cross-channel case), or the window expiring (no clock).
- Depends on static state left by other tests.
- Missing: `sendsAgainAfterWindow` (advance a fake clock 60 001 ms), `boundaryAt60000ms`, `emailDoesNotThrottleSms` (or the opposite, whichever is the decided rule), `differentUsersIndependent`, `failedSendDoesNotConsumeQuota`, and a concurrency test: 16 threads released by a `CountDownLatch` all call `sendEmail(sameUser)` -> exactly 1 send.

## Suggested shape

```java
public enum Channel { EMAIL, SMS, PUSH }
public enum SendResult { SENT, THROTTLED }

final class Throttle {
    private final ConcurrentHashMap<String, Long> lastSent = new ConcurrentHashMap<>();
    private final Clock clock;
    private final long windowMs;

    Throttle(Clock clock, Duration window) { this.clock = clock; this.windowMs = window.toMillis(); }

    /** Atomically reserves the slot. Returns the reservation token, or empty if throttled. */
    OptionalLong tryAcquire(String key) {
        long now = clock.millis();
        boolean[] won = {false};
        lastSent.compute(key, (k, prev) -> {          // runs atomically per key
            if (prev == null || now - prev >= windowMs) { won[0] = true; return now; }
            return prev;
        });
        return won[0] ? OptionalLong.of(now) : OptionalLong.empty();
    }

    /** Undo our own reservation only (no-op if someone else reserved since). */
    void release(String key, long token) { lastSent.remove(key, token); }
    // eviction of stale keys: scheduled sweep, or use Caffeine expireAfterWrite(window)
}

interface Sender { void send(User u, String msg); }

public class NotificationService {
    private final Map<Channel, Sender> senders;   // EMAIL -> (u, m) -> emailClient.send(u.getEmail(), m), etc.
    private final Throttle throttle;
    private final Metrics metrics;

    public SendResult send(User u, Channel ch, String msg) {
        String key = u.getId() + ":" + ch;
        OptionalLong token = throttle.tryAcquire(key);
        if (token.isEmpty()) { metrics.increment("notification.throttled", ch.name()); return SendResult.THROTTLED; }
        try {
            senders.get(ch).send(u, msg);
            return SendResult.SENT;
        } catch (RuntimeException e) {
            throttle.release(key, token.getAsLong());   // transient failure should not block the user for a minute
            throw e;
        }
    }

    public SendResult sendEmail(User u, String msg) { return send(u, Channel.EMAIL, msg); }  // keep old API for callers
    public SendResult sendSms(User u, String msg)   { return send(u, Channel.SMS, msg); }
    public SendResult sendPush(User u, String msg)  { return send(u, Channel.PUSH, msg); }
}
```

`compute` on `ConcurrentHashMap` runs atomically per key, so 16 concurrent callers for the same user produce exactly one `SENT`. Different users do not contend.
