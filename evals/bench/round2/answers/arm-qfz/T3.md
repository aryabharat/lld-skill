# T3 Builder for `Point(x, y)`?

No.

Builder solves "too many constructor parameters, many of them optional, easy to pass in the wrong order". `Point` has two required parameters and an obvious order. A builder would add a nested class, a `build()` step, and a way to forget to set `y` (a runtime error instead of a compile error) — more code and a weaker guarantee than the constructor.

Use the language feature instead:

```java
public record Point(int x, int y) {}          // immutable, equals/hashCode/toString for free

Point p = new Point(3, 4);
```

If you want readable named construction, add static factories, not a builder:

```java
public record Point(int x, int y) {
    public static final Point ORIGIN = new Point(0, 0);
    public static Point of(int x, int y) { return new Point(x, y); }
    public Point withX(int nx) { return new Point(nx, y); }   // only if you need "copy with change"
}
```

When Builder would become reasonable: if `Point` grew into something like a `Shape`/`Marker` with many optional attributes (z, label, colour, style, metadata...), with defaults and validation across fields. Revisit then, not now.
