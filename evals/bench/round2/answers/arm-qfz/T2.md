# T2 Draw after 50 moves without a win

## What the code needs
One new rule in a short, readable method. There is no type/state `switch` here and no second or third variant of "end rule" yet, so this is not the moment for a `WinRule`/`EndCondition` strategy list. The smallest correct change is: know how many moves have been played since the last win check, and add one condition.

Two things to get right:
1. **Order**: a win on the 50th move must still be a win, so the new check goes *after* the win checks, next to the existing draw check.
2. **Where the count lives**: "moves without a win" — in this game a win ends the game, so it equals "moves played". The count belongs to the `Board` (it already knows `lastPlayer()` and `isFull()`, so it already tracks moves). The engine should not keep its own counter: `getState(Board)` is a pure function of the board today and should stay that way (no hidden mutable state, safe to call twice).
3. The magic number becomes a named constant (or constructor parameter if product wants it configurable).

## Change

```java
class GameEngine {
  static final int MAX_MOVES_WITHOUT_WIN = 50;

  GameState getState(Board b) {
    if (rowWin(b)) return GameState.win(b.lastPlayer());
    if (colWin(b)) return GameState.win(b.lastPlayer());
    if (diagWin(b)) return GameState.win(b.lastPlayer());
    if (revDiagWin(b)) return GameState.win(b.lastPlayer());
    if (b.isFull() || b.moveCount() >= MAX_MOVES_WITHOUT_WIN) return GameState.draw();
    return GameState.inProgress();
  }
}
```

```java
class Board {
  private int moveCount;            // incremented in the existing place-mark method

  void place(int row, int col, Player p) {
    // ... existing validation and placement ...
    lastPlayer = p;
    moveCount++;
  }

  int moveCount() { return moveCount; }
}
```

If `Board` cannot be changed (third-party), I would pass the count in: `getState(Board b, int movesPlayed)` from the game loop that already counts turns, rather than storing a counter in the engine.

If the rule really means "50 moves since the last capture/win event" (chess-style, game continues after a scoring event), the board would track `movesSinceLastWin` and reset it on that event; the engine line stays the same.

## Tests
- `drawAfter50MovesWithoutWin`: play 50 non-winning moves on a board large enough not to be full -> `draw()`.
- `inProgressAt49Moves` -> `inProgress()` (boundary).
- `winOnFiftiethMoveIsWin` -> `win(player)`, proves the ordering.
- Existing tests for row/col/diag win and full-board draw unchanged and still green.

## When I would refactor further
If a third or fourth end rule arrives (time limit, resignation, repetition), turn the chain into an ordered `List<EndRule>` where each returns `Optional<GameState>`. With one extra `||` today that would be more code and harder to read than the change above.
