# T8 Refactor DiscountCalculator

## Diagnosis
- **Smell**: one method that every marketing change edits (a new `if` per week) — OCP violation with a real, recurring cost: every change risks the other rules and needs a full re-test.
- **Two new requirements the current shape cannot express**:
  1. *Non-stacking*: rules are just summed; there is no place to say "X does not combine with Y".
  2. *Audit*: it returns a single `double`; finance cannot see which rules applied, nor that the 30 % cap cut something.
- Also: `double` for money (rounding errors in finance reports), magic numbers, string coupon comparisons repeated.

This is the textbook Strategy signal (a list of interchangeable rules that keeps growing), so a small rule interface is justified here. I keep it to **one interface, one class per rule, one engine** — no factory hierarchy, no rule DSL.

## Step 0: lock current behaviour
Before touching it, write characterisation tests for the existing method (premium, >1000, each coupon, festive outside October, first order, combinations, cap hit). The refactor must keep them green; the new stacking behaviour is then added as a separate, reviewed change.

## Design

```java
/** One marketing rule. Stateless; new rule = new class + register it. */
public interface DiscountRule {
    String id();                                   // stable id for finance reports, e.g. "PREMIUM_10"
    Optional<String> exclusiveGroup();             // rules sharing a group do not stack: best one wins
    Optional<BigDecimal> discountFor(Order o);     // empty = not applicable
}

public record AppliedDiscount(String ruleId, BigDecimal amount) {}

public record DiscountResult(BigDecimal total,
                             List<AppliedDiscount> applied,      // what finance stores per order
                             List<String> suppressedRuleIds,     // eligible but lost to a better rule in its group
                             BigDecimal cappedBy) {}             // how much the cap removed (0 if none)
```

```java
public final class DiscountCalculator {
    private static final BigDecimal MAX_SHARE = new BigDecimal("0.30");
    private final List<DiscountRule> rules;

    public DiscountCalculator(List<DiscountRule> rules) { this.rules = List.copyOf(rules); }

    public DiscountResult discount(Order o) {
        // 1. evaluate every rule
        List<AppliedDiscount> eligible = new ArrayList<>();
        Map<String, AppliedDiscount> bestPerGroup = new LinkedHashMap<>();
        List<String> suppressed = new ArrayList<>();

        for (DiscountRule r : rules) {
            Optional<BigDecimal> amt = r.discountFor(o);
            if (amt.isEmpty() || amt.get().signum() <= 0) continue;
            AppliedDiscount a = new AppliedDiscount(r.id(), amt.get());

            if (r.exclusiveGroup().isEmpty()) { eligible.add(a); continue; }
            // 2. non-stacking: keep the largest within each group
            bestPerGroup.merge(r.exclusiveGroup().get(), a, (cur, cand) -> {
                if (cand.amount().compareTo(cur.amount()) > 0) { suppressed.add(cur.ruleId()); return cand; }
                suppressed.add(cand.ruleId()); return cur;
            });
        }
        eligible.addAll(bestPerGroup.values());

        // 3. cap
        BigDecimal sum = eligible.stream().map(AppliedDiscount::amount).reduce(BigDecimal.ZERO, BigDecimal::add);
        BigDecimal cap = o.total().multiply(MAX_SHARE).setScale(2, RoundingMode.HALF_UP);
        BigDecimal total = sum.min(cap);

        return new DiscountResult(total, List.copyOf(eligible), List.copyOf(suppressed), sum.subtract(total));
    }
}
```

## The existing rules, one small class each

```java
final class PremiumMemberRule implements DiscountRule {
    public String id() { return "PREMIUM_10_PCT"; }
    public Optional<String> exclusiveGroup() { return Optional.empty(); }
    public Optional<BigDecimal> discountFor(Order o) {
        return o.user().isPremium() ? Optional.of(pct(o.total(), "0.10")) : Optional.empty();
    }
}

final class LargeOrderRule implements DiscountRule {
    public String id() { return "ORDER_OVER_1000_FLAT_50"; }
    public Optional<String> exclusiveGroup() { return Optional.empty(); }
    public Optional<BigDecimal> discountFor(Order o) {
        return o.total().compareTo(new BigDecimal("1000")) > 0 ? Optional.of(new BigDecimal("50")) : Optional.empty();
    }
}

/** Covers WELCOME and FESTIVE (and next week's coupon) as data, not as new classes. */
final class CouponRule implements DiscountRule {
    private final String code; private final Predicate<Order> when; private final Function<Order, BigDecimal> amount;
    CouponRule(String code, Predicate<Order> when, Function<Order, BigDecimal> amount) { this.code = code; this.when = when; this.amount = amount; }

    public String id() { return "COUPON_" + code; }
    public Optional<String> exclusiveGroup() { return Optional.of("COUPON"); }     // one coupon per order
    public Optional<BigDecimal> discountFor(Order o) {
        return code.equals(o.coupon()) && when.test(o) ? Optional.of(amount.apply(o)) : Optional.empty();
    }
}

final class FirstOrderRule implements DiscountRule {
    public String id() { return "FIRST_ORDER_FLAT_25"; }
    public Optional<String> exclusiveGroup() { return Optional.empty(); }
    public Optional<BigDecimal> discountFor(Order o) {
        return o.user().orders() == 0 ? Optional.of(new BigDecimal("25")) : Optional.empty();
    }
}

final class Discounts {   // static import Discounts.pct
    static BigDecimal pct(BigDecimal total, String p) { return total.multiply(new BigDecimal(p)).setScale(2, RoundingMode.HALF_UP); }
}
```

Wiring (one place marketing changes touch):

```java
@Bean DiscountCalculator discountCalculator() {
    return new DiscountCalculator(List.of(
        new PremiumMemberRule(),
        new LargeOrderRule(),
        new CouponRule("WELCOME", o -> true,                                   o -> pct(o.total(), "0.05")),
        new CouponRule("FESTIVE", o -> o.date().getMonth() == Month.OCTOBER,   o -> new BigDecimal("100")),
        new FirstOrderRule()
    ));
}
```

Behaviour is identical to the old method (coupons were already mutually exclusive, since an order has one coupon; everything else stacks; 30 % cap), except money is now `BigDecimal` and the result explains itself.

## How the weekly requests land
- New rule: one class (or one `CouponRule` line), one test, one line in the wiring. No existing rule edited.
- "Rule X must not stack with Y": give both the same `exclusiveGroup`. If marketing needs "this rule excludes *everything*", add a group `"EXCLUSIVE_ALL"`-style flag in the engine *when that request actually arrives* — not now.
- Finance: persist `DiscountResult.applied` (rule id + amount) and `cappedBy` per order, e.g. an `order_discounts(order_id, rule_id, amount)` table. If they need the cap reduction allocated back to each rule, add pro-rata allocation in step 3.

## What I did not do (and when I would)
- **Rules from a database/config UI**: only once marketing wants to ship rules without a deploy. The `DiscountRule` interface is the seam for it; `CouponRule` is already halfway there.
- **Priority/ordering between rules**: not needed while discounts are additive and capped at the end; needed if percentage rules start applying "after" flat ones.
- **Rule engine library (Drools etc.)**: far more complexity than five-to-fifty rules need.

## Tests
- Characterisation tests from step 0, now asserting `result.total()`.
- Per rule: applies / does not apply (e.g. FESTIVE in September -> empty; order of exactly 1000 -> no flat 50).
- Stacking: two rules in the same group -> only the larger in `applied`, the other in `suppressedRuleIds`.
- Cap: sum above 30 % -> `total == 0.30 * orderTotal`, `cappedBy` = difference, `applied` still lists all rules.
- Audit: `applied` ids match exactly the expected rule ids for a premium first-time order with WELCOME.
- Money: no rounding drift (e.g. 0.10 of 999.99 -> 100.00 with HALF_UP).
