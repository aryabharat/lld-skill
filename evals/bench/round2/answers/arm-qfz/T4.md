# T4 Order status: State pattern?

## Short answer
Not the classic State pattern (one class per state). Use an **enum with an explicit transition table** for the lifecycle, and a small **Observer** (listener list) for "notify customer, restaurant, and later analytics".

## Why
State pattern pays off when an object's *behaviour* differs per state — many methods each with a `switch(status)` (e.g. "price changes in COOKING", "refund rules differ per state", "ETA calculated differently"). Here, from the requirements, the only state-dependent thing is **which transitions are legal**. That is data, not behaviour. Six State classes would each contain mostly "throw IllegalTransition" methods (an ISP/LSP smell) and spread a 7-line table over six files.

The thing that *will* grow is the set of reactions to a change (customer, restaurant, analytics, maybe SMS/ETA service). That is exactly Observer's signal: one change, many dependants, dependants added later without editing `Order`.

## Design

```java
public enum OrderStatus {
    PLACED, CONFIRMED, COOKING, PICKED, DELIVERED, CANCELLED;

    private static final Map<OrderStatus, Set<OrderStatus>> NEXT = new EnumMap<>(OrderStatus.class);
    static {
        NEXT.put(PLACED,    EnumSet.of(CONFIRMED, CANCELLED));
        NEXT.put(CONFIRMED, EnumSet.of(COOKING,   CANCELLED));
        NEXT.put(COOKING,   EnumSet.of(PICKED,    CANCELLED));
        NEXT.put(PICKED,    EnumSet.of(DELIVERED));
        NEXT.put(DELIVERED, EnumSet.noneOf(OrderStatus.class));
        NEXT.put(CANCELLED, EnumSet.noneOf(OrderStatus.class));
    }

    public boolean canMoveTo(OrderStatus to) { return NEXT.get(this).contains(to); }
    public boolean isTerminal() { return NEXT.get(this).isEmpty(); }
}
```

```java
public record OrderStatusChanged(String orderId, OrderStatus from, OrderStatus to, Instant at) {}

public interface OrderStatusListener {
    void onStatusChanged(OrderStatusChanged event);
}
```

```java
public class Order {
    private final String id;
    private OrderStatus status = OrderStatus.PLACED;
    private long version;                       // optimistic lock column

    OrderStatusChanged transitionTo(OrderStatus to, Clock clock) {
        if (!status.canMoveTo(to))
            throw new IllegalStateTransitionException(id, status, to);
        OrderStatus from = status;
        status = to;
        return new OrderStatusChanged(id, from, to, clock.instant());
    }
    public OrderStatus status() { return status; }
}
```

```java
public class OrderService {
    private final OrderRepository repo;
    private final List<OrderStatusListener> listeners;   // injected; analytics = add one bean
    private final Clock clock;

    public void changeStatus(String orderId, OrderStatus to) {
        Order o = repo.load(orderId);
        OrderStatusChanged ev = o.transitionTo(to, clock);
        repo.save(o);                                   // UPDATE ... WHERE id=? AND version=?  -> fails on concurrent change
        for (OrderStatusListener l : listeners) {
            try { l.onStatusChanged(ev); }
            catch (RuntimeException e) { log.warn("listener {} failed for {}", l, ev, e); }  // one bad listener does not block others
        }
    }
}

class CustomerNotifier   implements OrderStatusListener { public void onStatusChanged(OrderStatusChanged e) { /* push/SMS */ } }
class RestaurantNotifier implements OrderStatusListener { public void onStatusChanged(OrderStatusChanged e) { /* tablet/app */ } }
// later: class AnalyticsPublisher implements OrderStatusListener { ... }  — no change to Order or OrderService
```

Points worth calling out:
- **Concurrency**: "cancel" from the customer and "picked" from the rider can race. The optimistic `version` check makes one of them fail cleanly; the loser reloads and re-validates (CANCELLED -> PICKED is then rejected by the table).
- **Notify after commit**: listeners run after `save` succeeds, so nobody is told about a change that rolled back. In production I would write the event to an outbox table in the same transaction and deliver asynchronously (retries, and a slow SMS provider does not slow the API). The listener interface stays the same.
- Listener failures are isolated and logged, not propagated.

## When I would switch to State classes
If per-state *behaviour* appears — e.g. `cancel()` refunds fully in PLACED, partially in COOKING; `estimateEta()` differs per status; edits allowed only in PLACED — and those `switch(status)` blocks start appearing in several methods. Then move that behaviour into per-state objects; the transition table and the listener design above stay.

## Tests
- Every legal transition succeeds (parameterised over the table).
- Every illegal pair throws (e.g. PLACED->PICKED, DELIVERED->CANCELLED, CANCELLED->anything).
- Listeners receive exactly one event with correct from/to; a throwing listener does not stop the others.
- No event when the transition is illegal or the save fails.
- Concurrent cancel vs pick on the same order: exactly one wins.
