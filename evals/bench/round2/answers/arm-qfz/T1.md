# T1 Parking lot: fee calculation and spot allocation

## Assumptions
- Single process owns allocation for one lot (gates are threads, or requests to one service instance). If several service instances share a DB, the same idea moves into the DB (see "Multi-instance" at the end).
- A bike fits a bike spot; a car a car spot; a truck a large spot. (A "car can take a large spot if no car spot" fallback is an easy extension, shown as an ordered preference list.)
- Fee is computed at exit from entry time, exit time and vehicle type. Weekday/weekend is decided by the entry date (stated rule; product can change it in one place).
- Money is `BigDecimal` / long paise, never `double`.

## Smells and real pain (why the design looks like this)
1. Pricing is a dimension that is *already* known to grow (night rate, member discount, event surcharge are announced). A `switch(vehicleType) + if(weekend)` would be edited every week -> OCP pain is real, so a small rule abstraction is justified. Vehicle type x day type is *data*, not classes: a rate table, not `CarWeekendPricing` subclasses.
2. Two gates can pick the same free spot -> a race. This is the critical correctness issue; it needs an atomic "claim" operation, not a pattern.

Everything else (floors, spots, tickets) stays plain classes. No factory, no singleton.

## Key types

```java
enum VehicleType { BIKE, CAR, TRUCK }
enum SpotSize   { SMALL, MEDIUM, LARGE }

record Vehicle(String plate, VehicleType type) {}

final class Spot {
    final String id; final int floor; final SpotSize size;
    Spot(String id, int floor, SpotSize size) { this.id = id; this.floor = floor; this.size = size; }
}

record Ticket(String id, Vehicle vehicle, Spot spot, Instant entryAt) {}
record Money(long paise) {
    Money plus(Money o) { return new Money(paise + o.paise); }
    Money times(BigDecimal f) { return new Money(f.multiply(BigDecimal.valueOf(paise)).setScale(0, RoundingMode.HALF_UP).longValueExact()); }
    static final Money ZERO = new Money(0);
}
```

## Spot allocation (critical path, concurrency-safe)

One free-spot pool per `SpotSize`. `ConcurrentLinkedDeque.pollFirst()` is atomic: two gates calling it at the same moment can never get the same spot. No global lock, gates for different sizes never contend.

```java
final class SpotAllocator {
    private final Map<SpotSize, ConcurrentLinkedDeque<Spot>> free = new EnumMap<>(SpotSize.class);
    private final Map<VehicleType, List<SpotSize>> fits = Map.of(
        VehicleType.BIKE,  List.of(SpotSize.SMALL),
        VehicleType.CAR,   List.of(SpotSize.MEDIUM, SpotSize.LARGE),   // preference order
        VehicleType.TRUCK, List.of(SpotSize.LARGE));

    SpotAllocator(Collection<Spot> spots) {
        for (SpotSize s : SpotSize.values()) free.put(s, new ConcurrentLinkedDeque<>());
        // lower floors first: sort once, deque keeps the order
        spots.stream().sorted(Comparator.comparingInt((Spot s) -> s.floor))
             .forEach(s -> free.get(s.size).addLast(s));
    }

    Optional<Spot> allocate(VehicleType t) {
        for (SpotSize size : fits.get(t)) {
            Spot s = free.get(size).pollFirst();      // atomic claim
            if (s != null) return Optional.of(s);
        }
        return Optional.empty();                      // lot full for this type
    }

    void release(Spot s) { free.get(s.size).addFirst(s); }  // nearest spot reused first
}
```

Why not "scan floors and `synchronized` on the lot": correct but serialises every gate. Why not per-spot `AtomicBoolean` + scan: also correct, but O(spots) per entry. The deque gives O(1) atomic claim and is simpler. If "nearest to this gate" is required later, replace the deque by a per-gate-sorted structure behind the same `allocate` method; callers do not change.

Double release guard: the `ParkingLot` removes the ticket from `active` with `remove(id)` (atomic) and only the thread that got a non-null ticket releases the spot, so a retried exit request cannot put a spot back twice.

```java
final class ParkingLot {
    private final SpotAllocator allocator;
    private final FeeCalculator fees;
    private final Clock clock;
    private final ConcurrentHashMap<String, Ticket> active = new ConcurrentHashMap<>();

    Optional<Ticket> enter(Vehicle v) {
        return allocator.allocate(v.type()).map(spot -> {
            Ticket t = new Ticket(UUID.randomUUID().toString(), v, spot, clock.instant());
            active.put(t.id(), t);
            return t;
        });
    }

    Money exit(String ticketId, Customer c) {
        Ticket t = active.remove(ticketId);
        if (t == null) throw new IllegalStateException("unknown or already closed ticket " + ticketId);
        Money fee = fees.calculate(new ParkingSession(t, clock.instant(), c));
        allocator.release(t.spot());
        return fee;
    }
}
```

`Clock` is injected so tests control time (DIP where it actually buys testability).

## Fee calculation

Base price = rate table (vehicle type x day type) x billable hours. The announced extras are *adjustments on top of the base*, so they are a list of small rules applied in order. That is the minimal Strategy: one interface, one class per rule, a calculator that folds over them. Adding "event surcharge" = one new class + one line of wiring, no edit to existing rules.

```java
enum DayType { WEEKDAY, WEEKEND }

record ParkingSession(Ticket ticket, Instant exitAt, Customer customer) {
    Duration duration() { return Duration.between(ticket.entryAt(), exitAt); }
    long billableHours() { long m = duration().toMinutes(); return Math.max(1, (m + 59) / 60); } // round up, min 1h
}

final class RateTable {
    private final Map<VehicleType, Map<DayType, Money>> hourly;
    private final ZoneId zone;
    RateTable(Map<VehicleType, Map<DayType, Money>> hourly, ZoneId zone) { this.hourly = hourly; this.zone = zone; }

    Money base(ParkingSession s) {
        DayOfWeek d = s.ticket().entryAt().atZone(zone).getDayOfWeek();
        DayType dt = (d == DayOfWeek.SATURDAY || d == DayOfWeek.SUNDAY) ? DayType.WEEKEND : DayType.WEEKDAY;
        Money perHour = hourly.get(s.ticket().vehicle().type()).get(dt);
        return new Money(perHour.paise() * s.billableHours());
    }
}

/** A pricing adjustment applied after the base fee. */
interface PricingRule {
    Money apply(ParkingSession s, Money current);
}

final class FeeCalculator {
    private final RateTable rates;
    private final List<PricingRule> rules;          // order matters: surcharges, then discounts
    FeeCalculator(RateTable rates, List<PricingRule> rules) { this.rates = rates; this.rules = List.copyOf(rules); }

    Money calculate(ParkingSession s) {
        Money fee = rates.base(s);
        for (PricingRule r : rules) fee = r.apply(s, fee);
        return fee.paise() < 0 ? Money.ZERO : fee;
    }
}
```

The rules product announced, each a few lines:

```java
final class NightRateRule implements PricingRule {      // flat night fee if any part of stay is 22:00-06:00
    private final Money nightFee; private final ZoneId zone;
    public Money apply(ParkingSession s, Money cur) { return overlapsNight(s) ? cur.plus(nightFee) : cur; }
    private boolean overlapsNight(ParkingSession s) { /* walk hours between entry and exit in zone */ return false; }
}

final class EventSurchargeRule implements PricingRule {
    private final EventCalendar events; private final BigDecimal factor;  // e.g. 1.5
    public Money apply(ParkingSession s, Money cur) {
        return events.isEventDay(s.ticket().entryAt()) ? cur.times(factor) : cur;
    }
}

final class MemberDiscountRule implements PricingRule {
    private final BigDecimal pct;  // 0.20
    public Money apply(ParkingSession s, Money cur) {
        return s.customer().isMember() ? cur.times(BigDecimal.ONE.subtract(pct)) : cur;
    }
}
```

What I deliberately did **not** add: a `PricingStrategyFactory`, a class per vehicle type, or a rule engine/DSL. When rules start needing "this one excludes that one" or an audit of which rule applied, the `apply` can return a `(Money, appliedRuleName)` line item; not before.

## Tests I would write
Allocation
- `allocatesMediumForCar`, `carFallsBackToLargeWhenNoMedium`, `bikeNeverGetsLargeSpot`, `returnsEmptyWhenFull`.
- `releaseMakesSpotAvailableAgain`; `exitTwiceThrowsAndDoesNotDoubleRelease` (second `exit` throws, pool size unchanged).
- Concurrency: lot with N spots, 8 threads x many `enter` calls started together via `CountDownLatch`; assert number of successful tickets == N and all spot ids distinct. Repeat in a loop (e.g. 200 runs) to shake races.
- Concurrency mixed: threads entering and exiting concurrently; at the end `free + active == total` and no spot appears in both.

Fees (fixed `Clock`, no sleeping)
- Table-driven: each `VehicleType x {Wednesday, Saturday}` gives expected base.
- Billing rounding: 0 min -> 1h, 61 min -> 2h, exactly 60 min -> 1h.
- Weekday->weekend crossing uses entry day (documents the rule).
- Each rule in isolation: night rule applies at 23:00, not at 21:00; event surcharge only on calendar day; member discount only for members.
- Ordering: event surcharge then member discount gives the expected number (pins the order).
- Fee never negative.

## Multi-instance note
If several app instances serve the gates, in-memory deques no longer guarantee uniqueness. Then claim in the DB atomically:
`UPDATE spot SET ticket_id = ? WHERE id = (SELECT id FROM spot WHERE size = ? AND ticket_id IS NULL ORDER BY floor LIMIT 1 FOR UPDATE SKIP LOCKED) RETURNING id;`
`SpotAllocator` keeps the same interface; only its implementation changes.
