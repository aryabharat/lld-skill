# T4: Order status: State pattern?

## Short answer
No, not the classic GoF State pattern (one class per state). The states here do not behave differently; they only differ in which next states are allowed. That is data, not behaviour. A State class hierarchy would give you six small classes that each say "from here you may go to X or CANCELLED", and the full lifecycle would be scattered across six files. That is a shallow design: lots of interface for very little hidden logic.

What I would pick:
1. An enum that owns the transition table, so the whole lifecycle is readable in one place.
2. An `Order` that is the only way to change status, so the rule cannot be bypassed.
3. A single event (`OrderStatusChanged`) published after each change, with customer, restaurant and (later) analytics as subscribers. The order does not know who listens.

## Assumptions
- Notifications are side effects and must not be able to block or roll back a status change. In production the event goes through an outbox/queue; in-process listeners are shown here.
- Repeating the same transition (e.g. a retried CONFIRM) is a no-op, not an error. Retries are common in delivery systems.
- An illegal transition (e.g. DELIVERED -> COOKING) is a real bug or a race and is reported to the caller.

## Design

```java
public enum OrderStatus {
    PLACED, CONFIRMED, COOKING, PICKED, DELIVERED, CANCELLED;

    // The whole lifecycle in one place.
    private static final Map<OrderStatus, Set<OrderStatus>> NEXT = Map.of(
        PLACED,    EnumSet.of(CONFIRMED, CANCELLED),
        CONFIRMED, EnumSet.of(COOKING, CANCELLED),
        COOKING,   EnumSet.of(PICKED, CANCELLED),
        PICKED,    EnumSet.of(DELIVERED),
        DELIVERED, EnumSet.noneOf(OrderStatus.class),
        CANCELLED, EnumSet.noneOf(OrderStatus.class));

    public boolean canMoveTo(OrderStatus next) { return NEXT.get(this).contains(next); }
    public boolean isTerminal() { return NEXT.get(this).isEmpty(); }
}

public record OrderStatusChanged(String orderId, OrderStatus from, OrderStatus to, Instant at) {}

public interface OrderEventListener {
    void onStatusChanged(OrderStatusChanged event);
}

public final class Order {
    private final String id;
    private OrderStatus status = OrderStatus.PLACED;

    Order(String id) { this.id = id; }

    /**
     * Moves the order to {@code next}.
     * Returns the change event, or empty if the order is already in {@code next} (retries are harmless).
     * Throws IllegalStateException if the lifecycle does not allow this move.
     */
    synchronized Optional<OrderStatusChanged> moveTo(OrderStatus next, Clock clock) {
        if (status == next) return Optional.empty();
        if (!status.canMoveTo(next))
            throw new IllegalStateException("order " + id + ": cannot go from " + status + " to " + next);
        OrderStatus from = status;
        status = next;
        return Optional.of(new OrderStatusChanged(id, from, next, clock.instant()));
    }

    public OrderStatus status() { return status; }
}

/** The only entry point callers use. Hides persistence, locking and fan-out of notifications. */
public final class OrderService {
    private final OrderRepository repo;
    private final List<OrderEventListener> listeners;   // customer, restaurant; analytics added by config
    private final Clock clock;

    public void confirm(String id)  { change(id, OrderStatus.CONFIRMED); }
    public void startCooking(String id) { change(id, OrderStatus.COOKING); }
    public void pickUp(String id)   { change(id, OrderStatus.PICKED); }
    public void deliver(String id)  { change(id, OrderStatus.DELIVERED); }
    public void cancel(String id)   { change(id, OrderStatus.CANCELLED); }

    private void change(String id, OrderStatus next) {
        Order order = repo.get(id);
        Optional<OrderStatusChanged> event = order.moveTo(next, clock);
        if (event.isEmpty()) return;
        repo.save(order);       // in production: same transaction writes the event to an outbox table
        for (OrderEventListener l : listeners) {
            try { l.onStatusChanged(event.get()); }
            catch (RuntimeException e) { log.warn("listener {} failed for {}", l, event.get(), e); }
        }
    }
}
```

Listeners:
- `CustomerNotifier` and `RestaurantNotifier` implement `OrderEventListener` and decide the message text per transition (e.g. the restaurant does not care about PICKED -> DELIVERED but the customer does).
- Analytics later is one new class registered in the listener list. No change to `Order` or `OrderService`.

## Why this and not the State pattern
Design it twice:

| | State pattern | Enum transition table |
|---|---|---|
| Where the lifecycle lives | spread across 6 classes | one map |
| Adding a state (e.g. `READY_FOR_PICKUP`) | new class + edit neighbours | one enum value + one table line |
| Behaviour per state | yes, if needed | not needed today |
| Notifications | would tempt per-state notify code | one event, any number of subscribers |

Switch to State classes when states start having real behaviour of their own: e.g. COOKING computes an ETA from the kitchen, PICKED tracks a rider location, cancellation from COOKING triggers a partial refund calculation. Until then the table is the deeper, simpler module.

## Tests
- Every allowed transition succeeds; parameterised test over all (from, to) pairs asserts the rest throw.
- `cancel` works from PLACED, CONFIRMED, COOKING and throws from PICKED and DELIVERED.
- Calling `confirm` twice: one event, no exception.
- A throwing listener does not stop the status change or the other listeners.
- Adding a fake analytics listener receives every event without changing other code.
