# T3: Builder for Point(x, y)?

No.

A Builder pays for itself when a constructor has many parameters, several of them optional, or when values of the same type are easy to mix up. `Point` has two required values and nothing optional. A builder would make the most common use (creating a point) longer and would add a second class that does nothing except forward two values to the constructor, which is a shallow module.

```java
// Builder: more code for callers, and you can forget a field and still compile
Point p = Point.builder().x(3).y(4).build();

// What you want
Point p = new Point(3, 4);
```

Write it as a record:

```java
public record Point(double x, double y) {
    public static final Point ORIGIN = new Point(0, 0);

    public Point translate(double dx, double dy) { return new Point(x + dx, y + dy); }
}
```

This gives you immutability, `equals`/`hashCode`/`toString`, and one obvious way to construct it.

If the worry is readability at call sites, these are cheaper answers than a builder:
- Mixing up `x` and `y` is rare because the order is a universal convention. 
- If you need other ways to make a point, add named static factories: `Point.polar(r, theta)`, `Point.of(x, y)`.
- If validation is needed (e.g. no NaN), put it in the record's compact constructor, so every point is valid however it is made.

Revisit only if `Point` grows several optional fields (say `z`, `label`, `srid`, `precision`). Even then, for 3 to 4 fields, a couple of factory methods usually beats a builder.
