# T8: Refactoring DiscountCalculator

## What is wrong today
- **Change amplification**: every weekly rule edits the same method, and every rule author must understand all the others plus the 30% cap.
- **No record of what applied**: the method returns one number, so finance cannot see which rules gave what, or that the cap cut the total.
- **No way to express "does not stack"**: the only combination rule is "add everything, cap at 30%".
- **Money as `double`**: rounding errors in financial amounts. Use `BigDecimal`.
- Small issues: coupon codes are magic strings compared in each rule; `o.date().getMonth() == Month.OCTOBER` only works if `date()` is a `LocalDate`.

## Assumptions
- Current behaviour is correct and must be kept exactly: all rules stack, then the total is capped at 30% of the order total.
- "Must not stack" means: rules in the same **exclusivity group** compete, and only the largest in the group applies. (E.g. all coupon rules are one group; a future "flash sale" might share a group with the premium discount.) This covers the common cases with one concept. If marketing later needs "rule X cancels everything", that is a group rule too (see below).
- The cap is applied last and is reported as its own line, so the lines always add up to the final discount.

## Design

Two pieces, with the split chosen by who changes them:
- `DiscountRule`: one small class per marketing rule. This is what changes weekly. A rule only answers "do I apply to this order, and for how much?". It knows nothing about stacking, the cap or other rules.
- `DiscountCalculator`: the stable, deep part. It owns combining (groups), the cap and the audit trail. Callers still make one call.

```java
public record AppliedDiscount(String ruleId, BigDecimal amount) {}

/** Result of pricing an order's discounts. Lines always sum to total(). */
public record DiscountResult(List<AppliedDiscount> lines) {
    public BigDecimal total() {
        return lines.stream().map(AppliedDiscount::amount).reduce(BigDecimal.ZERO, BigDecimal::add);
    }
}

public interface DiscountRule {
    /** Stable id stored with the order for finance, e.g. "PREMIUM_10". Never reuse an id for different logic. */
    String id();

    /** Rules with the same group do not stack: only the largest applies. Empty means it stacks with everything. */
    default Optional<String> exclusivityGroup() { return Optional.empty(); }

    /** The discount this rule gives on its own, or empty if it does not apply. */
    Optional<BigDecimal> amountFor(Order order);
}
```

The calculator:

```java
public final class DiscountCalculator {
    static final String CAP_RULE_ID = "CAP_30_PERCENT";
    private static final BigDecimal MAX_SHARE = new BigDecimal("0.30");

    private final List<DiscountRule> rules;

    public DiscountCalculator(List<DiscountRule> rules) {
        Set<String> ids = new HashSet<>();
        for (DiscountRule r : rules)
            if (!ids.add(r.id())) throw new IllegalArgumentException("duplicate rule id " + r.id());
        this.rules = List.copyOf(rules);
    }

    public DiscountResult discount(Order order) {
        // 1. Every rule that applies, on its own.
        List<AppliedDiscount> candidates = new ArrayList<>();
        Map<String, AppliedDiscount> bestPerGroup = new LinkedHashMap<>();
        for (DiscountRule rule : rules) {
            Optional<BigDecimal> amount = rule.amountFor(order).filter(a -> a.signum() > 0);
            if (amount.isEmpty()) continue;
            AppliedDiscount line = new AppliedDiscount(rule.id(), amount.get());
            rule.exclusivityGroup().ifPresentOrElse(
                group -> bestPerGroup.merge(group, line,
                        (a, b) -> b.amount().compareTo(a.amount()) > 0 ? b : a),  // ties: first rule listed wins
                () -> candidates.add(line));
        }
        candidates.addAll(bestPerGroup.values());

        // 2. Cap, recorded as its own negative line so finance sees it.
        BigDecimal sum = candidates.stream().map(AppliedDiscount::amount).reduce(BigDecimal.ZERO, BigDecimal::add);
        BigDecimal cap = order.total().multiply(MAX_SHARE);
        if (sum.compareTo(cap) > 0) candidates.add(new AppliedDiscount(CAP_RULE_ID, cap.subtract(sum)));

        return new DiscountResult(List.copyOf(candidates));
    }
}
```

The existing rules become small, independent classes:

```java
final class PremiumMemberDiscount implements DiscountRule {
    public String id() { return "PREMIUM_10"; }
    public Optional<BigDecimal> amountFor(Order o) {
        return o.user().isPremium() ? Optional.of(o.total().multiply(new BigDecimal("0.10"))) : Optional.empty();
    }
}

final class LargeOrderDiscount implements DiscountRule {
    public String id() { return "ORDER_OVER_1000"; }
    public Optional<BigDecimal> amountFor(Order o) {
        return o.total().compareTo(new BigDecimal("1000")) > 0 ? Optional.of(new BigDecimal("50")) : Optional.empty();
    }
}

final class FirstOrderDiscount implements DiscountRule {
    public String id() { return "FIRST_ORDER_25"; }
    public Optional<BigDecimal> amountFor(Order o) {
        return o.user().orders() == 0 ? Optional.of(new BigDecimal("25")) : Optional.empty();
    }
}

/** General coupon rule: one class covers WELCOME, FESTIVE and every future coupon. */
final class CouponDiscount implements DiscountRule {
    private final String code;
    private final Predicate<Order> eligible;
    private final Function<Order, BigDecimal> amount;

    CouponDiscount(String code, Predicate<Order> eligible, Function<Order, BigDecimal> amount) {
        this.code = code; this.eligible = eligible; this.amount = amount;
    }
    public String id() { return "COUPON_" + code; }
    public Optional<String> exclusivityGroup() { return Optional.of("COUPON"); }
    public Optional<BigDecimal> amountFor(Order o) {
        return code.equals(o.coupon()) && eligible.test(o) ? Optional.of(amount.apply(o)) : Optional.empty();
    }
}
```

Wiring, the one place to look to see which rules are live:

```java
@Bean DiscountCalculator discountCalculator() {
    return new DiscountCalculator(List.of(
        new PremiumMemberDiscount(),
        new LargeOrderDiscount(),
        new FirstOrderDiscount(),
        new CouponDiscount("WELCOME", o -> true, o -> o.total().multiply(new BigDecimal("0.05"))),
        new CouponDiscount("FESTIVE", o -> o.date().getMonth() == Month.OCTOBER, o -> new BigDecimal("100"))));
}
```

Caller and persistence:

```java
DiscountResult result = discountCalculator.discount(order);
order.applyDiscount(result.total());
orderDiscountRepository.saveAll(order.id(), result.lines());   // table order_discounts(order_id, rule_id, amount)
```

Storing the lines with the order answers finance's question permanently, including for orders priced under rules that were later removed.

## Choices and the alternatives I did not take
- **Not a Chain of Responsibility / decorator chain.** Chaining makes each rule depend on the order it runs in and hides the combining policy across all the links. Here rules are independent and the policy is in one method.
- **Not "each rule declares which rule ids it excludes".** Pairwise exclusions grow as n^2 and every new rule would have to know about existing ones (information leakage). Groups keep that knowledge in one label.
- **Not a rules engine or DB-driven rules yet.** At one rule a week, a small class plus a unit test is a 15-minute change. If marketing wants to create coupons without a deploy, `CouponDiscount` is already general enough to be built from a `coupons` table (code, eligibility window, percent or fixed amount); I would do that step only when asked.
- **Rounding**: amounts are kept at full precision and rounded once, by the caller, when charging (`setScale(2, HALF_UP)`), so the lines and the total agree.

## How I would do the refactor safely
1. Write characterisation tests against the current `double` version for a grid of orders (premium/not, total around 1000, each coupon, October/not, first order/not, totals where the cap bites). Assert the new `result.total()` matches to the paisa.
2. Introduce the new classes and switch the caller. Remove the old method in the same PR.
3. Then add the first non-stacking rule as its own small PR.

## Tests
- Each rule class: applies / does not apply, including FESTIVE outside October and a null coupon.
- Calculator: two rules in the same group, only the larger appears; tie keeps the first listed.
- Rules without a group all stack.
- Cap: lines include `CAP_30_PERCENT` with a negative amount and `total()` equals 30% of the order total.
- No rule applies: empty lines, total zero.
- Duplicate rule ids are rejected at construction.
- Characterisation grid from step 1.
