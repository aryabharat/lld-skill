# T5: Review of NotificationService

Summary: the throttle is not safe under concurrent request threads, it throttles across channels (an email blocks an SMS), it leaks memory, and it cannot be tested beyond the one case shown. The three methods are also the same code three times, which is how these bugs got copied three times. Requesting changes.

## Blocking

**1. `HashMap` shared across request threads (data race).**
`lastSent` is a `static HashMap` read and written from many threads with no synchronisation. Concurrent `put`s during a resize can lose entries or corrupt the table (on older JDKs, an infinite loop in `get`). At minimum this must be a `ConcurrentHashMap`.

**2. Check-then-act race: the throttle does not throttle under load.**
Even with a `ConcurrentHashMap`, two requests for the same user can both read "not sent in the last 60s", both call `send`, and both `put`. Worse, `lastSent` is written only after `send` returns, so the window for the race is the full latency of the email/SMS provider (hundreds of ms). The check and the reservation must be one atomic step, done before sending:

```java
boolean[] allowed = {false};
lastSent.compute(key, (k, last) -> {
    if (last != null && now - last < windowMs) return last;   // keep old timestamp, deny
    allowed[0] = true;
    return now;                                              // reserve the slot
});
```

**3. One timestamp per user, shared by all channels.**
`sendEmail` followed by `sendSms` within 60s silently drops the SMS. If a user gets an order email and then an OTP by SMS, the OTP is lost. I assume that is not intended; the key should be `(userId, channel)`. If it *is* intended ("at most one message of any kind per minute"), it needs a comment and a test, because nobody reading `sendSms` would guess it.

**4. Messages are dropped silently.**
`return` with no result means callers cannot tell "sent" from "throttled". Some messages (OTP, password reset, payment failure) must never be throttled. Return a result (`SENT` / `THROTTLED`) and let critical message types bypass or use a separate policy.

## Should fix

**5. Unbounded memory.** One entry per user forever. With millions of users this grows without limit. Entries older than the window are useless; evict them (Caffeine with `expireAfterWrite(window)`, or a periodic sweep of the `ConcurrentHashMap`).

**6. `static` state.** The map is shared by every instance, including between tests. The test above passes or fails depending on which test ran before it with the same user id. Make it an instance field and inject the throttle.

**7. Per-process only.** Behind a load balancer with N servers, a user can receive up to N messages per minute. Fine if the goal is "stop accidental double-sends from one request"; not fine if it is a product guarantee. If it must hold across servers, the same `Throttle` interface can be backed by Redis `SET key 1 NX PX 60000`.

**8. Time is not injectable.** `System.currentTimeMillis()` makes it impossible to test "allowed again after 60s" without sleeping. Inject a `Clock` (or `LongSupplier`).

**9. Duplication.** The three methods differ only in the client and the address. Every fix above would need making three times. One throttle module plus one send path removes that.

## Suggested shape

```java
public enum Channel { EMAIL, SMS, PUSH }
public enum SendResult { SENT, THROTTLED }

/** Allows at most one message per (user, channel) per window. Thread-safe. */
final class Throttle {
    private final Cache<String, Long> lastSent;        // Caffeine: entries expire after the window
    private final Clock clock;
    private final long windowMs;

    Throttle(Clock clock, Duration window) {
        this.clock = clock; this.windowMs = window.toMillis();
        this.lastSent = Caffeine.newBuilder().expireAfterWrite(window).ticker(() -> clock.millis() * 1_000_000L).build();
    }

    /** Atomically checks and reserves the slot. Returns true if the caller may send now. */
    boolean tryAcquire(String userId, Channel channel) {
        long now = clock.millis();
        boolean[] allowed = {false};
        lastSent.asMap().compute(userId + ":" + channel, (k, last) -> {
            if (last != null && now - last < windowMs) return last;
            allowed[0] = true;
            return now;
        });
        return allowed[0];
    }
}

public class NotificationService {
    private final Throttle throttle;
    private final Map<Channel, ChannelSender> senders;   // EMAIL -> u -> emailClient.send(u.getEmail(), msg), etc.

    public SendResult send(User u, Channel channel, String msg) {
        if (!throttle.tryAcquire(u.getId(), channel)) return SendResult.THROTTLED;
        senders.get(channel).send(u, msg);
        return SendResult.SENT;
    }
}
```

Keep `sendEmail/sendSms/sendPush` as one-line wrappers if callers depend on them.

One decision to make explicitly: if `send` throws after the slot is reserved, the user is blocked for 60s without having received anything. For most notifications that is acceptable (and protects a failing provider from retries); for important ones, release the slot on failure.
