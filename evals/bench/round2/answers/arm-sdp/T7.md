# T7: Schema for organisations, members, teams and repository access

## Assumptions
- PostgreSQL.
- Only organisations own repositories (personal repos are out of scope; adding them later means an `owner` that is either a user or an org, see the end).
- Teams belong to one organisation, and a team can only be granted access to repositories of its own organisation.
- A user can be granted access to a repository without being a member of the org (an "outside collaborator"), as on GitHub.
- Org admins have admin access to every repository in their org. This is derived at query time, not copied into grant rows, so removing someone's admin role takes effect everywhere at once.
- Repo permission levels: `read < write < admin`.

## Tables

```sql
CREATE TYPE org_role  AS ENUM ('member', 'admin');
CREATE TYPE repo_perm AS ENUM ('read', 'write', 'admin');   -- declared in ascending order, so max() works

CREATE TABLE users (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  login       citext NOT NULL UNIQUE,                 -- case-insensitive unique handle
  email       citext NOT NULL UNIQUE,
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE organizations (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  login       citext NOT NULL UNIQUE,
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE org_memberships (
  org_id      bigint NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
  user_id     bigint NOT NULL REFERENCES users(id)         ON DELETE CASCADE,
  role        org_role NOT NULL DEFAULT 'member',
  created_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (org_id, user_id)
);
CREATE INDEX org_memberships_user_idx ON org_memberships (user_id);        -- "which orgs am I in?"

CREATE TABLE teams (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  org_id      bigint NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
  slug        citext NOT NULL,
  UNIQUE (org_id, slug),                    -- team names unique within an org; also serves "teams of org X"
  UNIQUE (org_id, id)                       -- target for the composite FK below
);

CREATE TABLE team_memberships (
  team_id     bigint NOT NULL REFERENCES teams(id) ON DELETE CASCADE,
  user_id     bigint NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  PRIMARY KEY (team_id, user_id)
);
CREATE INDEX team_memberships_user_idx ON team_memberships (user_id);      -- "which teams am I in?"

CREATE TABLE repositories (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  org_id      bigint NOT NULL REFERENCES organizations(id) ON DELETE RESTRICT,
  name        citext NOT NULL,
  visibility  text NOT NULL CHECK (visibility IN ('public', 'private', 'internal')),
  created_at  timestamptz NOT NULL DEFAULT now(),
  UNIQUE (org_id, name),                    -- "org/repo" lookup by URL; also covers "repos of org X"
  UNIQUE (org_id, id)
);

CREATE TABLE repo_user_grants (
  repo_id     bigint NOT NULL REFERENCES repositories(id) ON DELETE CASCADE,
  user_id     bigint NOT NULL REFERENCES users(id)        ON DELETE CASCADE,
  permission  repo_perm NOT NULL,
  granted_by  bigint REFERENCES users(id),
  granted_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (repo_id, user_id)            -- one grant per user per repo; change = UPDATE
);
CREATE INDEX repo_user_grants_user_idx ON repo_user_grants (user_id);

CREATE TABLE repo_team_grants (
  org_id      bigint NOT NULL,
  repo_id     bigint NOT NULL,
  team_id     bigint NOT NULL,
  permission  repo_perm NOT NULL,
  granted_by  bigint REFERENCES users(id),
  granted_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (repo_id, team_id),
  -- Same org_id in both FKs: a team can only be granted repos of its own org.
  FOREIGN KEY (org_id, repo_id) REFERENCES repositories (org_id, id) ON DELETE CASCADE,
  FOREIGN KEY (org_id, team_id) REFERENCES teams (org_id, id)        ON DELETE CASCADE
);
CREATE INDEX repo_team_grants_team_idx ON repo_team_grants (team_id);
```

## Why two grant tables instead of one polymorphic table

Design it twice. The alternative is one `repo_grants(repo_id, grantee_type, grantee_id, permission)`. It looks simpler, but `grantee_id` cannot have a foreign key, so deleting a user or team leaves orphan grants, and the "team must be in the same org" rule cannot be enforced. Two tables give real foreign keys, cascade deletes and the cross-org constraint, and the only cost is a `UNION` in one query, which lives in one view:

## The one access question, in one place

```sql
-- Effective permission of every user on every repo they can reach. Callers ask this view, not the grant tables.
CREATE VIEW effective_repo_access AS
SELECT user_id, repo_id, max(permission) AS permission
FROM (
  SELECT g.user_id, g.repo_id, g.permission FROM repo_user_grants g
  UNION ALL
  SELECT tm.user_id, tg.repo_id, tg.permission
  FROM repo_team_grants tg JOIN team_memberships tm ON tm.team_id = tg.team_id
  UNION ALL
  SELECT m.user_id, r.id, 'admin'::repo_perm
  FROM org_memberships m JOIN repositories r ON r.org_id = m.org_id
  WHERE m.role = 'admin'
) s
GROUP BY user_id, repo_id;
```

The hot query is "can user U do X on repo R?":
`SELECT permission FROM effective_repo_access WHERE user_id = $1 AND repo_id = $2`. With the indexes:
- direct grant: PK `(repo_id, user_id)` point lookup;
- team path: PK `(repo_id, team_id)` gives the repo's teams, then PK `(team_id, user_id)` checks membership;
- admin path: `repositories.id` gives `org_id`, then PK `(org_id, user_id)` on memberships.

All three are index point lookups, so the check costs a handful of index probes, even for large orgs. Public repos give `read` to everyone; that rule belongs in the application's `canRead` check next to this query, not as a grant row per user.

## Index rationale, summarised

| Index | Query it serves |
|---|---|
| `org_memberships (org_id, user_id)` PK | members of an org; admin check |
| `org_memberships (user_id)` | orgs of a user (dashboard, sign-in) |
| `teams (org_id, slug)` unique | team by name in URL; teams of an org |
| `team_memberships (team_id, user_id)` PK / `(user_id)` | team members / a user's teams |
| `repositories (org_id, name)` unique | resolve `org/repo` from URL; list an org's repos |
| `repo_user_grants (repo_id, user_id)` PK / `(user_id)` | access check, repo's collaborators / "repos shared with me" |
| `repo_team_grants (repo_id, team_id)` PK / `(team_id)` | repo's teams / team's repos, and cleanup when a team is deleted |

I add no other indexes until a real query needs one: every index slows writes and grant changes are frequent in big orgs.

## Notes
- **Removing a member from an org** must also remove their team memberships in that org (one transaction, in the membership module). Direct repo grants stay, which turns them into an outside collaborator; that is GitHub's behaviour and the product should confirm it.
- **"Repos user U can see" at scale**: the view is fine for a single check. For listing all repos a user can reach in a huge org, a materialised `user_repo_access` table maintained on grant/membership changes may be needed later; the view's interface stays the same.
- **Personal repositories later**: add `owner_user_id` beside `org_id` with `CHECK (num_nonnulls(org_id, owner_user_id) = 1)`, or introduce an `accounts` table that both users and orgs extend. I would decide that when it is needed.
