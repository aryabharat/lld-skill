# T8 Refactor `DiscountCalculator`

## What forces the change

Three things in the request, each with its own consequence:

1. **A new rule every week.** Each one is an edit to one well-tested function. That is a repeat request of the same kind, so the rules leave the calculator and become data: a list of rule objects, and one loop that does not know what any rule checks.
2. **Some rules must not stack.** So rules are not simply summed. The combine step must be explicit and must not depend on list order. I use exclusion groups: rules in the same group compete and only the largest applies; rules with no group always stack. (A first-match loop would be wrong here: it ignores every rule after the first, and its result depends on position.)
3. **Finance wants to know which rules applied.** A `double` cannot say that. The calculator returns a result record: each applied rule with its amount, the rules that lost in their group, and the cap adjustment.

Two fixes that come with it: money moves from `double` to `BigDecimal` (finance will reconcile these numbers), and the 30 % cap becomes a visible line in the result instead of a silent `Math.min`.

## Step 0: lock the current behaviour

Before moving anything, a characterisation test over the five current rules and the cap (cases listed under Tests). The first version of the refactor must give the same totals for every case. All five existing rules therefore start with **no** exclusion group, which is how they behave today. Grouping them (for example "WELCOME and first-order do not stack") is a product decision; it is one field per rule once decided.

## Code

Assumes `Order.total()` returns `BigDecimal` (if it is still `double`, wrap it once with `BigDecimal.valueOf` at the entry of `discount`) and `import static java.math.BigDecimal.ZERO`.

```java
/** One discount rule. Pure: reads the order, returns the amount it would give (zero if it does not apply). */
record DiscountRule(String id, String exclusionGroup /* null = always stacks */,
                    Function<Order, BigDecimal> amount) {
    DiscountRule {
        Objects.requireNonNull(id); Objects.requireNonNull(amount);
    }
    static DiscountRule stacking(String id, Function<Order, BigDecimal> amount) {
        return new DiscountRule(id, null, amount);
    }
    static DiscountRule exclusive(String id, String group, Function<Order, BigDecimal> amount) {
        return new DiscountRule(id, Objects.requireNonNull(group), amount);
    }
}

record AppliedDiscount(String ruleId, BigDecimal amount) {}

record DiscountResult(List<AppliedDiscount> applied,     // rules that contributed, in rule-list order
                      List<String> suppressed,           // rules that matched but lost in their group
                      BigDecimal beforeCap,
                      BigDecimal capAdjustment,          // zero, or the negative amount the cap removed
                      BigDecimal total) {}
```

The rules live in one file, one entry per rule. Adding next week's rule is one line here and no edit to the calculator:

```java
final class DiscountRules {
    static final BigDecimal CAP_RATE = new BigDecimal("0.30");

    static final List<DiscountRule> ALL = List.of(
        DiscountRule.stacking("PREMIUM_10_PCT",
            o -> o.user().isPremium() ? pct(o.total(), "0.10") : ZERO),
        DiscountRule.stacking("BIG_ORDER_50",
            o -> o.total().compareTo(new BigDecimal("1000")) > 0 ? new BigDecimal("50") : ZERO),
        DiscountRule.stacking("COUPON_WELCOME_5_PCT",
            o -> "WELCOME".equals(o.coupon()) ? pct(o.total(), "0.05") : ZERO),
        DiscountRule.stacking("COUPON_FESTIVE_OCT_100",
            o -> "FESTIVE".equals(o.coupon()) && o.date().getMonth() == Month.OCTOBER ? new BigDecimal("100") : ZERO),
        DiscountRule.stacking("FIRST_ORDER_25",
            o -> o.user().orders() == 0 ? new BigDecimal("25") : ZERO)
        // Example of a non-stacking rule once marketing asks for it:
        // DiscountRule.exclusive("DIWALI_15_PCT", "SEASONAL", o -> ...),
        // DiscountRule.exclusive("COUPON_FESTIVE_OCT_100", "SEASONAL", ...)   // only the larger of the two applies
    );

    private static BigDecimal pct(BigDecimal total, String rate) { return total.multiply(new BigDecimal(rate)); }
    private DiscountRules() {}
}
```

The calculator is now closed: evaluate every rule, resolve groups, sum, cap.

```java
final class DiscountCalculator {
    private final List<DiscountRule> rules;
    private final BigDecimal capRate;

    DiscountCalculator(List<DiscountRule> rules, BigDecimal capRate) {
        Set<String> ids = new HashSet<>();
        for (DiscountRule r : rules)
            if (!ids.add(r.id())) throw new IllegalArgumentException("duplicate rule id: " + r.id());
        this.rules = List.copyOf(rules);
        this.capRate = capRate;
    }

    DiscountCalculator() { this(DiscountRules.ALL, DiscountRules.CAP_RATE); }

    DiscountResult discount(Order o) {
        // 1. Evaluate every rule independently. Order of evaluation does not change any amount.
        List<AppliedDiscount> matched = new ArrayList<>();
        for (DiscountRule r : rules) {
            BigDecimal amt = r.amount().apply(o);
            if (amt.signum() < 0) throw new IllegalStateException("rule " + r.id() + " returned " + amt);
            if (amt.signum() > 0) matched.add(new AppliedDiscount(r.id(), amt));
        }

        // 2. In each exclusion group keep only the largest; ties go to the smaller rule id (deterministic).
        Map<String, DiscountRule> byId = rules.stream().collect(Collectors.toMap(DiscountRule::id, r -> r));
        Map<String, AppliedDiscount> winnerByGroup = new HashMap<>();
        for (AppliedDiscount a : matched) {
            String g = byId.get(a.ruleId()).exclusionGroup();
            if (g == null) continue;
            winnerByGroup.merge(g, a, (x, y) -> {
                int c = x.amount().compareTo(y.amount());
                if (c != 0) return c > 0 ? x : y;
                return x.ruleId().compareTo(y.ruleId()) <= 0 ? x : y;
            });
        }
        List<AppliedDiscount> applied = new ArrayList<>();
        List<String> suppressed = new ArrayList<>();
        for (AppliedDiscount a : matched) {
            String g = byId.get(a.ruleId()).exclusionGroup();
            if (g == null || winnerByGroup.get(g) == a) applied.add(a);
            else suppressed.add(a.ruleId());
        }

        // 3. Sum, then cap at capRate of the order total.
        BigDecimal beforeCap = applied.stream().map(AppliedDiscount::amount).reduce(ZERO, BigDecimal::add);
        BigDecimal cap = o.total().multiply(capRate);
        BigDecimal total = beforeCap.min(cap).setScale(2, RoundingMode.HALF_UP);
        BigDecimal capAdjustment = total.subtract(beforeCap.setScale(2, RoundingMode.HALF_UP));
        return new DiscountResult(List.copyOf(applied), List.copyOf(suppressed), beforeCap, capAdjustment, total);
    }
}
```

Callers that only need the number use `discount(o).total()`. Persist `applied`, `suppressed` and `capAdjustment` with the order (one row per applied rule) so finance can answer "which rules, how much, and was it capped".

Why this shape and not others:
- Not one class per rule: each rule is a condition and an amount; a record holding a function is enough. A rule that needs a collaborator (a member service, an event calendar) is a small class or a closure over it.
- Not Chain of Responsibility: every rule can apply, so there is no "first one answers".
- Not order-based precedence: the only interaction between rules is the exclusion group, and it is resolved by amount, so moving a line in `DiscountRules.ALL` cannot change any result.

`ponytail: rules in code, deployed weekly. If marketing must add rules without a deploy, move the parameters (thresholds, rates, coupon codes, date windows) into a table that feeds a small fixed set of rule kinds; do not build a general rule language.`

`skipped: per-user usage limits, rule start/end dates, percentage caps per group; add when requested.`

## Tests (through `discount`, scripted orders, no clock)

Characterisation, must match the old method on each case:
- premium user, total 500, no coupon: 50.00
- total 1200, non-premium: 50.00
- WELCOME coupon, total 400: 20.00
- FESTIVE coupon in October, total 400: 100.00; same in November: 0.00
- first order, total 200: 25.00
- premium + WELCOME + first order, total 100: 10 + 5 + 25 = 40, capped at 30.00

New behaviour:
- `reportsEachAppliedRule`: premium, total 1200: applied = [PREMIUM_10_PCT 120, BIG_ORDER_50 50], total 170.00.
- `capIsVisible`: the capped case above shows beforeCap 40, capAdjustment -10.00, total 30.00.
- `exclusiveGroupKeepsLargest`: two scripted rules in group "G" (20 and 35) plus one stacking rule (5): applied = 35 and 5, suppressed = the 20 rule, total 40.
- `exclusiveTieIsDeterministic`: two rules in one group with equal amounts: the smaller id wins, and reversing the list order gives the same result.
- `listOrderDoesNotChangeResult`: shuffle `DiscountRules.ALL` and compare totals over the characterisation orders.
- `duplicateRuleIdRejected` and `negativeAmountRejected`.

Use scripted rule lists in the group tests rather than the real marketing rules, so next week's rule change does not edit these tests.
