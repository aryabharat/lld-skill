# T7 Schema: organisations, members, teams, repositories, access grants

PostgreSQL. Order of work: features, then the queries that hit each table, then tables and indexes.

## Features and the queries they drive

| Feature | Hot query |
|---|---|
| Is user U a member/admin of org O? | lookup by (org, user) |
| List members of O; list orgs of U | by org; by user |
| Org owns repos; repo names unique per org | by (org, name) for URL resolution `org/repo` |
| Teams in an org; members of a team; teams of a user | by team; by user |
| Grant a repo to a user or to a team with a permission | by repo (settings page); by user / by team |
| **Can U do X on repo R?** (every git push/pull and page view) | the effective permission of (user, repo) |
| List repos U can access | by user, through direct and team grants |

Assumptions: a team belongs to exactly one org; teams are flat (no nested teams); a team can only be granted repos of its own org; a user grant may go to a non-member (an outside collaborator); org admins have admin on every repo of the org.

`skipped: nested teams, org-wide base permission, invitations, user-owned repos, audit log, soft delete; add when requested.`

## Tables

```sql
CREATE TABLE users (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    login       CITEXT NOT NULL UNIQUE,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE organisations (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    login       CITEXT NOT NULL UNIQUE,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- One row per (org, user). Role is a column, so a user cannot be both member and admin.
CREATE TABLE org_memberships (
    org_id      BIGINT NOT NULL REFERENCES organisations(id) ON DELETE CASCADE,
    user_id     BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    role        TEXT   NOT NULL CHECK (role IN ('member', 'admin')),
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (org_id, user_id)
);
CREATE INDEX org_memberships_user_idx ON org_memberships (user_id, org_id);   -- "my organisations"

CREATE TABLE repositories (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    org_id      BIGINT NOT NULL REFERENCES organisations(id) ON DELETE CASCADE,
    name        CITEXT NOT NULL,
    visibility  TEXT   NOT NULL CHECK (visibility IN ('public', 'private')),
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (org_id, name),          -- URL resolution; also serves "repos of an org"
    UNIQUE (id, org_id)             -- target for composite FKs that pin a grant to the same org
);

CREATE TABLE teams (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    org_id      BIGINT NOT NULL REFERENCES organisations(id) ON DELETE CASCADE,
    slug        CITEXT NOT NULL,
    UNIQUE (org_id, slug),
    UNIQUE (id, org_id)
);

-- A team member must be a member of the team's org: both composite FKs enforce it in the database.
-- Removing someone from the org cascades to their team memberships.
CREATE TABLE team_members (
    org_id      BIGINT NOT NULL,
    team_id     BIGINT NOT NULL,
    user_id     BIGINT NOT NULL,
    PRIMARY KEY (team_id, user_id),
    FOREIGN KEY (team_id, org_id) REFERENCES teams (id, org_id) ON DELETE CASCADE,
    FOREIGN KEY (org_id, user_id) REFERENCES org_memberships (org_id, user_id) ON DELETE CASCADE
);
CREATE INDEX team_members_user_idx ON team_members (user_id, team_id);   -- "teams of a user" (access check)

-- Permission as an ordered small integer so "highest of several grants" is MAX().
-- 1 read, 2 triage, 3 write, 4 maintain, 5 admin
CREATE TABLE repo_user_grants (
    repo_id     BIGINT   NOT NULL REFERENCES repositories(id) ON DELETE CASCADE,
    user_id     BIGINT   NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    permission  SMALLINT NOT NULL CHECK (permission BETWEEN 1 AND 5),
    granted_by  BIGINT   REFERENCES users(id) ON DELETE SET NULL,
    granted_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (repo_id, user_id)                -- one grant per pair; "who has access to R"
);
CREATE INDEX repo_user_grants_user_idx ON repo_user_grants (user_id, repo_id);

CREATE TABLE repo_team_grants (
    org_id      BIGINT   NOT NULL,
    repo_id     BIGINT   NOT NULL,
    team_id     BIGINT   NOT NULL,
    permission  SMALLINT NOT NULL CHECK (permission BETWEEN 1 AND 5),
    granted_by  BIGINT   REFERENCES users(id) ON DELETE SET NULL,
    granted_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (repo_id, team_id),
    FOREIGN KEY (repo_id, org_id) REFERENCES repositories (id, org_id) ON DELETE CASCADE,
    FOREIGN KEY (team_id, org_id) REFERENCES teams (id, org_id)        ON DELETE CASCADE  -- same org as the repo
);
CREATE INDEX repo_team_grants_team_idx ON repo_team_grants (team_id, repo_id);
```

## Why two grant tables and not one polymorphic table

A single `repo_grants(repo_id, grantee_type, grantee_id, permission)` cannot have a foreign key on `grantee_id`, so deleting a team or user leaves orphan grants, and nothing stops a grant to a team from another org. Two tables keep real FKs and cascades; the access query unions them, which is cheap. A table with two nullable columns (`user_id`, `team_id`) plus a CHECK that exactly one is set also works and keeps one table; I prefer two because each has a clean primary key.

Rejected: a list column (array of member ids) on organisations or teams: every membership check would scan or unnest the list, and there are no FKs.

## The access check

```sql
-- Effective permission of :user on :repo (NULL = no access; public repos add read in the app layer).
SELECT MAX(p) AS permission FROM (
    SELECT 5 AS p                                       -- org admin
    FROM repositories r
    JOIN org_memberships m ON m.org_id = r.org_id AND m.user_id = :user AND m.role = 'admin'
    WHERE r.id = :repo
  UNION ALL
    SELECT g.permission FROM repo_user_grants g
    WHERE g.repo_id = :repo AND g.user_id = :user       -- PK lookup
  UNION ALL
    SELECT g.permission FROM team_members tm
    JOIN repo_team_grants g ON g.team_id = tm.team_id AND g.repo_id = :repo
    WHERE tm.user_id = :user                            -- team_members_user_idx, then PK (repo_id, team_id)
) s;
```

Every branch is an index lookup: the repo PK plus the `org_memberships` PK; the `repo_user_grants` PK; `team_members_user_idx` (a user is in a handful of teams) then the `repo_team_grants` PK per team. No scan grows with org or repo size.

"Repos U can access" uses the same three sources keyed by user: `org_memberships_user_idx` (admin orgs, then `repositories (org_id, name)`), `repo_user_grants_user_idx`, and `team_members_user_idx` + `repo_team_grants_team_idx`.

## Index list, and why each exists

| Index | Serves |
|---|---|
| `users.login`, `organisations.login` UNIQUE | login and URL lookup; uniqueness |
| `org_memberships` PK (org_id, user_id) | membership/admin check, members of an org |
| `org_memberships (user_id, org_id)` | orgs of a user |
| `repositories (org_id, name)` UNIQUE | resolve `org/repo`, list repos of an org |
| `repositories (id, org_id)`, `teams (id, org_id)` UNIQUE | targets for the same-org composite FKs |
| `teams (org_id, slug)` UNIQUE | resolve `org/team`, list teams of an org |
| `team_members` PK (team_id, user_id) | members of a team; no duplicate membership |
| `team_members (user_id, team_id)` | teams of a user, the first hop of every access check |
| `repo_user_grants` PK (repo_id, user_id) | access check; "who has access" on the repo settings page |
| `repo_user_grants (user_id, repo_id)` | repos a user was granted |
| `repo_team_grants` PK (repo_id, team_id) | access check; repo settings page |
| `repo_team_grants (team_id, repo_id)` | repos of a team; cascade on team delete |

FK columns that lead a PK or a listed index are already covered, so cascaded deletes do not scan. No index on `permission` or `role`: they are read with the row, never searched by.

Normalised to third normal form: each fact lives in one row (role on the membership, permission on the grant). The only duplicated column is `org_id` on `team_members` and `repo_team_grants`, kept on purpose so the database can enforce "same org" through composite FKs.

## Notes for the application layer

- The access check runs on every git operation. If it shows up in profiles, cache the effective permission per (user, repo) with a short TTL and invalidate on grant, membership or team changes; do not denormalise it into a table first.
- Demoting the last admin of an org should be rejected in the service (a check with `SELECT ... FOR UPDATE` on the org's admin rows), since a CHECK constraint cannot express it.
