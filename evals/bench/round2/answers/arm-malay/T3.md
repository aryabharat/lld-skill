# T3 Builder for `Point(x, y)`?

No.

A Builder pays for itself when a type has many optional fields and several valid ways to build it, so constructors multiply and call sites pass placeholder `null`s or `false`s. `Point` has two required fields and one way to build it. A builder there adds a class, makes every call site longer, and makes it possible to forget `y` (so you need a runtime check that the constructor already gives you at compile time).

Use a record:

```java
public record Point(int x, int y) {}

Point p = new Point(3, 4);
Point moved = p.withX(5);   // only if you need copy-with-change:
                            // add  public Point withX(int x) { return new Point(x, y); }
```

You get immutability, `equals`/`hashCode`/`toString`, and a constructor that cannot be called with a field missing.

If readability at the call site is the worry (`new Point(3, 4)` versus a mixed-up order), a named factory is enough: `Point.of(x, y)`, or `Point.polar(r, theta)` when there is a second way to build it.

When to revisit: `Point` grows several optional attributes (label, colour, z, metadata) with sensible defaults, and you start writing constructor overloads or passing placeholders. Even then, first try one constructor plus `withX`-style methods; reach for a builder only when that becomes unwieldy.
