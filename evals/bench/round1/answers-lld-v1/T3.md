No. No pattern is needed here.

**The problem Builder solves** is constructor overloads multiplying as optional fields arrive, with callers passing `null`, `0` or `false` placeholders. `Point` has two required fields, one way to build it, and no defaults or validation logic. There is nothing for a builder to fix; it would add a nested class, a `build()` call that can be forgotten, and the chance to build a point with `y` missing.

**Use an immutable value type with a constructor:**

```java
public record Point(int x, int y) {
  public static final Point ORIGIN = new Point(0, 0);

  public Point translate(int dx, int dy) { return new Point(x + dx, y + dy); }
}

Point p = new Point(3, 4);
```

A record gives you `equals`, `hashCode` and `toString` for free, which matters if points go in sets or map keys. On older Java, a `final` class with two `final` fields and the same methods.

**Rejected:** Builder, for the reason above. Also rejected: a static factory `Point.of(x, y)` unless you need caching or a named alternative such as `Point.polar(r, theta)`. Then a named factory is the right tool, not a builder.

**Watch out:** if `Point` is easy to call with swapped arguments in your codebase (`new Point(row, col)` vs `(x, y)`), fix it with clear names (`GridPos(row, col)` as a separate type), not a builder. Revisit Builder only if the type grows several optional fields (label, colour, z, metadata) and constructors start to multiply.
