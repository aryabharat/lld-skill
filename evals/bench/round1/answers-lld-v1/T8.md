# Refactoring DiscountCalculator

## What hurts, mapped to the three asks

| Ask | Problem in today's code | Fix |
|---|---|---|
| A new rule every week | Every rule is an `if` in one method; each week's PR edits and re-tests the same tested code | Each rule is a class; the calculator loops over an injected list and never changes when a rule is added |
| Some rules must not stack | No place to express it; you would add flags and nested `if`s that reference other rules | A stacking policy applied after rules are evaluated: rules declare an exclusivity group, the policy keeps the best per group |
| Finance wants to know which rules applied | Returns one `double`; which rules fired, and whether the 30% cap cut anything, is lost | Return a `DiscountResult` with one line per rule (applied / suppressed / capped), persisted with the order |

Also fixed on the way:
- **Money as `double`.** `total * 0.10` produces values like 99.99999999. Use `long` paise (or `BigDecimal`) in a `Money` value object.
- **Coupon matched as raw strings** in two places with null checks. A coupon rule takes its code as a constructor argument.
- **The 30% cap is a policy hidden in the `return` line.** It becomes a named step that records how much it removed.

The rules today are independent: every one computes from the original total and none reads another's result. That is what makes a rule list safe here. If marketing ever wants "10% off the already-discounted total", that is ordering, and it must be explicit in the pipeline, not hidden in list order.

## Step 1: pin current behaviour

Before changing anything, characterisation tests on the old class with hand-computed numbers (current code, doubles):

- Premium, total 2 000, coupon WELCOME, first order: 200 + 50 + 100 + 25 = 375; cap 600 -> **375**.
- Total exactly 1 000, not premium, no coupon, not first order -> **0** (the flat 50 needs `> 1000`).
- FESTIVE in October, total 500, not first order -> 100; cap 150 -> **100**. FESTIVE in November -> **0**.
- Premium, total 200, first order: 20 + 25 = 45; cap 60 -> **45**. Premium, total 100, first order, FESTIVE in October: 10 + 100 + 25 = 135; cap **30**.
- No coupon (`null`) -> no NPE.

These run against the new code too; they must stay green except where we deliberately change rounding (paise instead of doubles).

## Step 2: the new shape

```java
public record Money(long paise) implements Comparable<Money> {
  public static final Money ZERO = new Money(0);
  public Money plus(Money o)       { return new Money(Math.addExact(paise, o.paise)); }
  public Money minus(Money o)      { return new Money(Math.subtractExact(paise, o.paise)); }
  public Money percent(int pct)    { return new Money(paise * pct / 100); }          // rounds down, documented
  public static Money rupees(long r) { return new Money(r * 100); }
  public int compareTo(Money o)    { return Long.compare(paise, o.paise); }
  public static Money min(Money a, Money b) { return a.compareTo(b) <= 0 ? a : b; }
}

/** One discount rule. Pure: reads the order, returns a candidate, never mutates anything. */
public interface DiscountRule {
  String id();                                              // stable id, stored for finance
  Optional<String> exclusivityGroup();                      // rules in the same group never stack
  Optional<Money> evaluate(Order order);                    // empty = rule does not apply
}

public record Candidate(String ruleId, Optional<String> group, Money amount) {}

public enum Outcome { APPLIED, SUPPRESSED, CAPPED }
public record DiscountLine(String ruleId, Money amount, Outcome outcome, String reason) {}

public record DiscountResult(Money total, List<DiscountLine> lines) {
  public List<DiscountLine> applied() {
    return lines.stream().filter(l -> l.outcome() == Outcome.APPLIED).toList();
  }
}
```

### Rules: today's five, each a small class

```java
final class PremiumMemberDiscount implements DiscountRule {
  public String id() { return "PREMIUM_10_PCT"; }
  public Optional<String> exclusivityGroup() { return Optional.empty(); }
  public Optional<Money> evaluate(Order o) {
    return o.user().isPremium() ? Optional.of(o.total().percent(10)) : Optional.empty();
  }
}

final class LargeOrderFlat implements DiscountRule {
  private final Money threshold = Money.rupees(1_000), flat = Money.rupees(50);
  public String id() { return "LARGE_ORDER_FLAT_50"; }
  public Optional<String> exclusivityGroup() { return Optional.empty(); }
  public Optional<Money> evaluate(Order o) {
    return o.total().compareTo(threshold) > 0 ? Optional.of(flat) : Optional.empty();
  }
}

/** Coupons share one group: an order gets at most one coupon discount. */
final class CouponPercent implements DiscountRule {
  private final String code; private final int pct;
  CouponPercent(String code, int pct) { this.code = code; this.pct = pct; }
  public String id() { return "COUPON_" + code; }
  public Optional<String> exclusivityGroup() { return Optional.of("COUPON"); }
  public Optional<Money> evaluate(Order o) {
    return code.equals(o.coupon()) ? Optional.of(o.total().percent(pct)) : Optional.empty();
  }
}

final class SeasonalCouponFlat implements DiscountRule {
  private final String code; private final Month month; private final Money flat;
  SeasonalCouponFlat(String code, Month month, Money flat) { this.code = code; this.month = month; this.flat = flat; }
  public String id() { return "COUPON_" + code; }
  public Optional<String> exclusivityGroup() { return Optional.of("COUPON"); }
  public Optional<Money> evaluate(Order o) {
    return code.equals(o.coupon()) && o.date().getMonth() == month ? Optional.of(flat) : Optional.empty();
  }
}

final class FirstOrderFlat implements DiscountRule {
  public String id() { return "FIRST_ORDER_FLAT_25"; }
  public Optional<String> exclusivityGroup() { return Optional.of("NEW_USER"); }
  public Optional<Money> evaluate(Order o) {
    return o.user().orders() == 0 ? Optional.of(Money.rupees(25)) : Optional.empty();
  }
}
```

`code.equals(o.coupon())` is null-safe, which removes the duplicated null checks. `o.date()` is the order's own date, so no clock is read.

### Stacking and cap: separate, named policies

```java
/** Decides which candidates survive. Default: best candidate per exclusivity group. */
public interface StackingPolicy {
  List<DiscountLine> resolve(List<Candidate> candidates);
}

final class BestPerGroup implements StackingPolicy {
  public List<DiscountLine> resolve(List<Candidate> candidates) {
    Map<String, Candidate> best = new HashMap<>();
    for (Candidate c : candidates)
      c.group().ifPresent(g -> best.merge(g, c, (a, b) -> a.amount().compareTo(b.amount()) >= 0 ? a : b));

    List<DiscountLine> lines = new ArrayList<>();
    for (Candidate c : candidates) {
      boolean kept = c.group().map(g -> best.get(g) == c).orElse(true);
      lines.add(kept
          ? new DiscountLine(c.ruleId(), c.amount(), Outcome.APPLIED, "")
          : new DiscountLine(c.ruleId(), c.amount(), Outcome.SUPPRESSED,
                             "lower than " + best.get(c.group().get()).ruleId() + " in group " + c.group().get()));
    }
    return lines;
  }
}

public final class DiscountCalculator {
  private final List<DiscountRule> rules;      // order does not matter: rules are independent
  private final StackingPolicy stacking;
  private final int capPercent;

  public DiscountCalculator(List<DiscountRule> rules, StackingPolicy stacking, int capPercent) {
    this.rules = List.copyOf(rules); this.stacking = stacking; this.capPercent = capPercent;
  }

  public DiscountResult discount(Order o) {
    List<Candidate> candidates = new ArrayList<>();
    for (DiscountRule r : rules)
      r.evaluate(o).ifPresent(m -> candidates.add(new Candidate(r.id(), r.exclusivityGroup(), m)));

    List<DiscountLine> lines = new ArrayList<>(stacking.resolve(candidates));
    Money sum = lines.stream().filter(l -> l.outcome() == Outcome.APPLIED)
                     .map(DiscountLine::amount).reduce(Money.ZERO, Money::plus);

    Money cap = o.total().percent(capPercent);
    Money total = Money.min(sum, cap);
    if (total.compareTo(sum) < 0)
      lines.add(new DiscountLine("CAP_" + capPercent + "_PCT", sum.minus(total), Outcome.CAPPED,
                                 "total discount capped at " + capPercent + "% of order"));
    return new DiscountResult(total, List.copyOf(lines));
  }
}
```

Wiring, in one place (or as DI-registered beans):

```java
new DiscountCalculator(List.of(
    new PremiumMemberDiscount(),
    new LargeOrderFlat(),
    new CouponPercent("WELCOME", 5),
    new SeasonalCouponFlat("FESTIVE", Month.OCTOBER, Money.rupees(100)),
    new FirstOrderFlat()),
  new BestPerGroup(), 30);
```

### Finance

Persist the result with the order in the same transaction as the order itself:

```sql
order_discounts(order_id, rule_id, amount_paise, outcome, reason, PRIMARY KEY (order_id, rule_id))
```

Finance gets every rule that fired, every rule that was suppressed and why, and how much the cap removed, per order. Rule ids are stable strings, so reports survive code changes; never reuse an id for a different rule.

## How the weekly change now looks

- **New rule:** one new class (often a new instance of an existing parameterised class such as `CouponPercent("DIWALI", 15)`) plus one line of wiring. `DiscountCalculator`, `BestPerGroup` and every existing rule are untouched, and their tests stay green.
- **"X must not stack with Y":** give both the same exclusivity group. If marketing needs "X stacks with nothing at all", add an `exclusive()` flag that `BestPerGroup` handles (if any exclusive rule wins, everything else is suppressed); that is one change to the policy, not to every rule.
- **Cap changes or per-rule caps:** constructor parameter, or a `CapPolicy` interface if caps start to vary by user segment.

## Patterns used and rejected

- **Rule list + small engine:** used. The rules are independent checks, each able to say "not me", and every feature was editing the same function.
- **Chain of Responsibility:** rejected. That is "first match wins in priority order"; here many rules apply together.
- **Decorator per rule (`new FestiveDiscount(new PremiumDiscount(base))`):** rejected. Order of wrapping becomes behaviour, the audit trail is hard to extract, and each new rule changes the construction chain.
- **Rules as data in a DB / admin dashboard now:** deferred. Worth it when marketing wants to launch rules without a deploy; the shape above is the step before it (parameterised rule types with a type tag, deserialised through a registry, with scope and validity dates in indexed columns). A code list gets most of the benefit today.

**Watch out:** the list is order-free only while rules are independent. If a rule ever needs the running total (percent-after-flat), do not rely on list order silently; add an explicit stage (`preDiscountRules`, `postDiscountRules`) and a test that pins it.

## Tests

- The characterisation numbers above, now asserting `DiscountResult.total()` and the exact set of applied rule ids.
- Each rule, table-driven, on its own: premium/non-premium; total 999.99 / 1 000 / 1 000.01; coupon `null`, wrong code, right code; FESTIVE in September/October/November; first order vs second.
- `BestPerGroup`: two candidates in one group keeps the larger and marks the other SUPPRESSED with a reason; ungrouped candidates all apply; tie keeps a deterministic winner.
- Cap: sum below cap has no CAPPED line; sum above cap returns exactly 30% and a CAPPED line equal to the difference (premium, total 100, first order, FESTIVE October: 135 -> 30, CAPPED 105).
- `Money` on its own: `plus`, `percent` rounding, overflow.
- Adding a fake sixth rule in a test changes the result without any change to `DiscountCalculator` (the extensibility check, as a test).
