# Adding "draw after 50 moves without a win"

## The smell this request exposes

The one-line fix works:

```java
if (b.moveCount() >= 50) return GameState.draw();   // after the win checks, before inProgress
```

But this is the second end-of-game condition added by editing `getState`, and the chain will keep growing (threefold repetition, resignation, timeouts, variant boards). Every new rule means opening and re-testing the same method. That is a growing if-chain: each check is independent, returns early, and differs only in its condition. The fix is to make each check a rule object and have `getState` loop over an injected, ordered list. The engine then knows how to evaluate rules, not what they are, and the 50-move rule becomes one new class plus one line of wiring.

The checks are not fully order-free: a win on the 50th move must be a win, not a draw. So the list is ordered (wins first, then draws), the order is built in one place, and a test pins it. I keep a `List`, never a `Set`.

## Step 1: pin current behaviour

Before touching `getState`, add characterisation tests on boards built directly (no AI, no system clock): row, column, diagonal and anti-diagonal wins return `win(lastPlayer)`; full board with no line returns `draw`; partial board returns `inProgress`; a board that is full *and* has a winning line returns `win` (order matters).

## Step 2: refactor with no behaviour change

```java
/** One end-of-game condition. Empty means "this rule has nothing to say". */
interface GameRule {
  Optional<GameState> evaluate(Board b);
}

final class LineWinRule implements GameRule {
  private final Predicate<Board> line;          // rowWin, colWin, diagWin, revDiagWin
  LineWinRule(Predicate<Board> line) { this.line = line; }
  public Optional<GameState> evaluate(Board b) {
    return line.test(b) ? Optional.of(GameState.win(b.lastPlayer())) : Optional.empty();
  }
}

final class FullBoardDraw implements GameRule {
  public Optional<GameState> evaluate(Board b) {
    return b.isFull() ? Optional.of(GameState.draw()) : Optional.empty();
  }
}

class GameEngine {
  private final List<GameRule> rules;           // ordered: first decisive rule wins

  GameEngine(List<GameRule> rules) { this.rules = List.copyOf(rules); }

  GameState getState(Board b) {
    for (GameRule rule : rules) {
      Optional<GameState> state = rule.evaluate(b);
      if (state.isPresent()) return state.get();
    }
    return GameState.inProgress();
  }
}
```

The existing `rowWin/colWin/diagWin/revDiagWin` bodies move unchanged into a `LineChecks` helper and are passed as predicates. Run the characterisation tests: they must pass untouched.

## Step 3: the new rule

```java
final class MoveLimitDraw implements GameRule {
  private final int maxMoves;
  MoveLimitDraw(int maxMoves) {
    if (maxMoves <= 0) throw new IllegalArgumentException("maxMoves must be positive: " + maxMoves);
    this.maxMoves = maxMoves;
  }
  public Optional<GameState> evaluate(Board b) {
    return b.moveCount() >= maxMoves ? Optional.of(GameState.draw()) : Optional.empty();
  }
}

final class StandardRules {
  /** Win rules must come before draw rules: a winning 50th move is a win. */
  static List<GameRule> create(int maxMovesWithoutWin) {
    return List.of(
        new LineWinRule(LineChecks::rowWin),
        new LineWinRule(LineChecks::colWin),
        new LineWinRule(LineChecks::diagWin),
        new LineWinRule(LineChecks::revDiagWin),
        new FullBoardDraw(),
        new MoveLimitDraw(maxMovesWithoutWin));
  }
}

GameEngine engine = new GameEngine(StandardRules.create(50));
```

`Board` needs `moveCount()`. The board already applies moves, so it owns the counter: increment it inside `board.move(...)`, the one mutation path. I would not derive it from filled cells, because a game with captures or removals would undercount. If the board already keeps a move history, return `history.size()` instead of adding a field.

The limit is a constructor argument, not a literal inside the rule, so a variant with 30 or 100 moves (or none: leave the rule out) is a wiring change.

Assumption: "50 moves" means 50 moves in total by both players. If product means 50 per player, the rule compares `moveCount() >= 2 * 50`; the class name and test change, nothing else.

## Tests for the new behaviour

Build boards directly with a scripted move list and no AI:

- 49 moves, no line: `inProgress`.
- 50 moves, no line: `draw`.
- 50th move completes a row: `win(lastPlayer)`, not draw (pins rule order).
- 51st call after a draw: still `draw` (and `move` must refuse moves once the game is over; check that guard exists).
- Full board before 50 moves (3x3 fills at 9): `draw` from `FullBoardDraw`, unchanged.
- `MoveLimitDraw(0)` throws.
- `MoveLimitDraw` on its own, table-driven over 0, 49, 50, 51 moves.
- `StandardRules.create(50)` returns win rules before draw rules (one golden test on the order).

## Rejected

- **The one-line `if`:** fine if this were the last rule ever. It is the second draw rule in a short time, so the chain is where the next change will hurt; the refactor costs about 40 lines and removes that.
- **A `Set<GameRule>` or a fully configurable rule DSL:** a set loses the win-before-draw order; a DSL is over-engineering for six rules that a code list handles.
- **Wrapping `getState` in a `MoveLimitGameEngine`:** wrappers stack up per request and the core becomes untouchable.
