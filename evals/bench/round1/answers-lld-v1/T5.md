# Review: NotificationService throttling

**What this change does.** Adds a per-user throttle: a user gets at most one notification per 60 seconds, across email, SMS and push, tracked in a static in-memory map of last-send times. Each channel method checks the map, sends, then records the time.

**Load assumed.** Many request threads in one JVM calling these methods concurrently, and (as is usual for a web tier) more than one server instance behind a load balancer.

## Must fix

### 1. `HashMap` shared across request threads (`lastSent`, all three methods)
- **Problem:** `lastSent` is a static `HashMap` read and written by many request threads with no synchronisation. Concurrent `put`s during a resize can lose entries or corrupt the table, and a thread may never see another thread's write (no happens-before), so the throttle silently stops working under load. It is also shared by every instance of the service and across every test in the JVM.
- **Fix:** move the state into a dedicated throttle object holding a `ConcurrentHashMap`, injected into the service (not static). See the sketch under finding 2.
- **Rule:** shared mutable state needs a named mechanism; single-key independent operations -> concurrent map.

### 2. Check-then-act race sends duplicates (all three methods)
- **Problem:** the check (`now - lastSent < 60_000`), the send and the `put` are three separate steps. Two requests for the same user arriving together both read "no recent send", both send, both write. This happens even with a `ConcurrentHashMap`, because each call is atomic but the sequence is not. The window is the whole duration of `emailClient.send`, which is a network call, so with a slow provider (say 800 ms) every request in that window gets through. A retrying client or a double-clicked button hits it routinely.
- **Fix:** reserve the slot atomically before sending; roll the reservation back if the send fails.
  ```java
  final class Throttle {
    private final ConcurrentHashMap<ThrottleKey, Long> lastSent = new ConcurrentHashMap<>();
    private final Clock clock;
    private final long windowMs;

    /** Returns the reservation stamp, or empty if throttled. Atomic per key. */
    OptionalLong tryAcquire(ThrottleKey key) {
      long now = clock.millis();
      boolean[] granted = {false};
      lastSent.compute(key, (k, prev) -> {
        if (prev != null && now - prev < windowMs) return prev;   // still inside the window
        granted[0] = true;
        return now;                                               // reserve before sending
      });
      return granted[0] ? OptionalLong.of(now) : OptionalLong.empty();
    }
    void cancel(ThrottleKey key, long stamp) { lastSent.remove(key, stamp); }   // only our own reservation
  }
  ```
  `compute` runs the whole decide-and-write under the map's per-key lock, so exactly one of N concurrent callers wins. Keep the lambda tiny: no IO inside it.
- **Rule:** check-then-act must be one atomic step per key.

### 3. Request threads block on email/SMS/push IO
- **Problem:** `emailClient.send` etc. run on the web server's request thread. Request pools are small; when the SMS provider slows to seconds, a burst of notifications drains the pool and unrelated pages queue behind it (head-of-line blocking).
- **Fix:** return `CompletableFuture<SendResult>` and run the provider call on a bounded, named executor per channel (or enqueue to a notification queue/worker). The request thread only does the throttle check and the hand-off. Give every provider call a timeout.
- **Rule:** never block a request thread on IO; IO methods return futures.

### 4. Throttled messages are dropped silently
- **Problem:** `return;` with `void` means the caller cannot tell "sent" from "throttled", and nothing is logged. A password-reset or OTP SMS sent 30 seconds after a marketing email simply disappears, and the user is locked out with no trace.
- **Fix:** return a result (`SENT`, `THROTTLED`, `FAILED`) so callers can decide, and log/meter throttled sends. Decide with product which message types bypass the throttle (transactional vs promotional); pass that as a message priority, not as another `if` in each method.
- **Rule:** more than two outcomes -> result object, not void/boolean.

### 5. One throttle shared across all channels
- **Problem:** the key is only `userId`, so an email blocks the SMS and the push for the next 60 s. Case: order confirmation email at t=0, "your delivery partner is here" push at t=40 s is dropped. If the intent really is "one notification of any kind per minute", that needs to be written down; I suspect it is a copy-paste side effect.
- **Fix:** key by `(userId, channel)` (the `ThrottleKey` above), or by `(userId, messageType)` if product wants that. Make the choice explicit in one place.
- **Rule:** name the narrowest key that carries the guarantee.

## Should fix

### 6. Wall clock read inside logic, twice per call
- **Problem:** `System.currentTimeMillis()` is called in the check and again in the `put`, so the recorded time is later than the time used to decide, and the expiry path cannot be tested without sleeping 60 s. That is why the test only covers "two sends in a row".
- **Fix:** inject a `Clock`, read it once per operation.
- **Rule:** never read the system clock in domain code or tests.

### 7. Three copies of the same method; a new channel means a fourth
- **Problem:** the methods differ only in which client and which address field they use. Adding WhatsApp copies the throttle logic again, and the next fix (finding 2) has to be made three times; one copy will be missed. The service also decides *whether* to send and *how* to send, two reasons to change.
- **Fix:** a `Channel` interface (`send(User, String) -> CompletableFuture<Void>`, plus `ChannelType type()`), one `send(User u, ChannelType c, String msg)` entry point, and the throttle as its own injected class:
  ```java
  public CompletableFuture<SendResult> send(User u, ChannelType type, String msg) {
    ThrottleKey key = new ThrottleKey(u.getId(), type);
    OptionalLong stamp = throttle.tryAcquire(key);
    if (stamp.isEmpty()) return CompletableFuture.completedFuture(SendResult.THROTTLED);
    return channels.get(type).send(u, msg)
        .thenApply(v -> SendResult.SENT)
        .exceptionally(e -> { throttle.cancel(key, stamp.getAsLong()); return SendResult.FAILED; });
  }
  ```
  Keep `sendEmail/sendSms/sendPush` as one-line delegates if callers depend on them.
- **Rule:** a new variant should be an addition, not a copy of tested code.

### 8. Map grows forever
- **Problem:** one entry per user who ever received a notification, never removed. With millions of users this is a slow memory leak in every web node.
- **Fix:** entries older than the window are useless; use an expiring cache (e.g. Caffeine with `expireAfterWrite(60s)`, whose `asMap().compute` keeps the atomic reservation), or a periodic sweep removing entries older than the window.
- **Rule:** every index needs a removal path.

### 9. Throttle is per JVM, not per user
- **Problem:** with N web servers behind a load balancer, each has its own map, so a user can receive N notifications per minute; the throttle's strength depends on deployment size.
- **Fix:** if the limit must hold globally, keep the reservation in a shared store with an atomic set-if-absent and TTL (for example Redis `SET key 1 NX PX 60000`), or move sending to a notification worker partitioned by user id so one process owns each user. If per-node is acceptable, document it.
- **Rule:** state the guarantee and what it does not cover.

### 10. Tests are thin and non-deterministic
- **Problem:** the test relies on two real-time calls landing within 60 s, shares the static map with every other test (another test that emailed `user` first changes the result), and covers one path.
- **Fix:** fresh `Throttle` and fake `Clock` per test, and add:
  - send at t=0, t=59 999 ms -> throttled; t=60 000 ms -> sent (boundary of `<`);
  - different users are independent;
  - channel behaviour as decided in finding 5 (email then SMS);
  - failed send does not consume the window (next send goes out);
  - 50 threads call `send` for the same user behind a start latch -> exactly one `SENT`, 49 `THROTTLED`, one provider call (repeat many times);
  - a slow fake provider does not block the calling thread.
- **Rule:** inject time; concurrency tests run many interleavings and assert returned values.

## Nice to have

### 11. Name the window
`60_000` appears three times. Make it a constructor parameter (`Duration window`) so ops can tune it and tests can shrink it.

## Verdict

**Ship after must-fixes** (1-5). Findings 6, 7 and 10 come almost free with the fix for 2 and should land in the same PR; 8 and 9 can follow if the window and deployment size are confirmed.

## Skipped on purpose

- A token bucket or sliding-window rate limiter library: the requirement is "one per minute", which a last-send timestamp expresses exactly. Revisit if product asks for "3 per hour".
- A full notification queue with retry and DLQ: worth it once delivery guarantees matter, but not required to make this change correct.
- Typed id wrappers for `userId`: low value for this change.

## Not checked

- Callers of these methods and whether any of them rely on the silent drop or on cross-channel throttling.
- Whether `emailClient`, `smsClient` and `pushClient` are thread-safe and whether they already have timeouts.
