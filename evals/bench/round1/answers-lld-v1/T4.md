# Order status: State pattern or not?

**The problem in one line.** You need (a) only legal transitions to happen and (b) every transition to reach a set of consumers that will grow. Those are two separate problems, and the State pattern only addresses the first.

**Pick: a status enum that owns its transition table, one `Order.transitionTo` choke point, an append-only status log, and Observer for the fan-out.**

- The graph is small and sparse (6 states, 7 edges), which is where State *could* fit. But nothing else about the order behaves differently per state today: each state class would contain only "which states may I go to next". Six classes holding one set each is the enum's job with more files.
- Notifications are a different axis. Customer, restaurant and later analytics are consumers whose set changes over time, which is exactly what Observer is for. The order code publishes one event and never imports the consumers. Adding analytics is a new listener plus one registration line.
- Current status lives on the order as the single source of truth; history goes to an append-only log written in the same transaction, so "when was it confirmed?" never needs a second state machine.

**Rejected: State pattern** (one class per status with `confirm()`, `cook()`, `cancel()`...). It earns its place when behaviour, not just legality, differs per state: for example if cancelling from COOKING must charge the restaurant's cost, cancelling from PLACED is a free void, and each state has different allowed edits (address change only before COOKING). If those rules arrive and start showing up as `if (status == ...)` branches in several services, move to State then. Today it would copy a transition table into six classes and every new state would touch several of them. Also rejected: calling `notifyCustomer(); notifyRestaurant();` directly in the status method, because analytics would mean editing tested order code.

**Sketch:**

```java
enum OrderStatus {
  PLACED, CONFIRMED, COOKING, PICKED, DELIVERED, CANCELLED;
  private static final Map<OrderStatus, Set<OrderStatus>> NEXT = Map.of(
      PLACED,    EnumSet.of(CONFIRMED, CANCELLED),
      CONFIRMED, EnumSet.of(COOKING, CANCELLED),
      COOKING,   EnumSet.of(PICKED, CANCELLED),
      PICKED,    EnumSet.of(DELIVERED),
      DELIVERED, EnumSet.noneOf(OrderStatus.class),
      CANCELLED, EnumSet.noneOf(OrderStatus.class));
  boolean canMoveTo(OrderStatus to) { return NEXT.get(this).contains(to); }
}

interface OrderStatusListener { void onStatusChanged(OrderStatusChanged e); }   // Customer, Restaurant, Analytics

final class OrderService {
  private final OrderRepository orders; private final OrderEvents events; private final Clock clock;

  void transition(OrderId id, OrderStatus from, OrderStatus to, String reason) {
    if (!from.canMoveTo(to)) throw new IllegalTransitionException(id, from, to);
    // one transaction: UPDATE orders SET status=:to WHERE id=:id AND status=:from; INSERT order_status_log ...
    if (!orders.compareAndSetStatus(id, from, to, reason, clock.instant()))
      throw new ConcurrentTransitionException(id, from, to);      // someone else moved it first
    events.publish(new OrderStatusChanged(id, from, to, reason, clock.instant()));
  }
}
```

`OrderEvents` holds a `CopyOnWriteArrayList<OrderStatusListener>` and calls each listener in its own `try/catch`, so a failing SMS gateway cannot stop the restaurant notification.

**Watch out:**

- **Concurrent transitions.** The customer cancels at the same moment the restaurant confirms. The conditional update on `from` makes exactly one win; the loser gets a clear error and re-reads. Without it you get a CONFIRMED order that was also refunded.
- **Slow or failing listeners.** Under synchronous dispatch one slow consumer blocks the transition and one exception stops the rest. Isolate each listener (own try/catch, own executor) and publish only after the DB commit. Once customer and restaurant notification live in other services, replace in-process Observer with an outbox table plus a broker, so a crash between commit and publish does not lose the event.
- **Do not make the order observe itself**, and do not use Observer for a fixed single recipient. It is justified here only because the consumer set is already two and growing.
- Tests: every legal edge succeeds, every illegal edge (DELIVERED -> CANCELLED, PICKED -> CANCELLED, PLACED -> COOKING) throws; each listener fires exactly once per transition; one throwing listener does not stop the others; two threads racing CANCELLED vs CONFIRMED from PLACED produce exactly one success and one log row.
